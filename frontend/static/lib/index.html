@tm/sdk

version …

The typed, zero-dependency JavaScript client for the TaskManager API — every /v1 route as a function, an orchestrator loop in one call, and an MCP tool factory. Node 20+, Deno, Bun and browsers.

Pointing an agent at this? Give it /llms-full.txt — the whole operating context in one file (what this software is, how to get a token, the three doors, a runnable orchestrator, the full generated reference and the rules of the house). The same thing as a readable page is at /integrate, a short index at /llms.txt, and a machine manifest at /integrate.json.
Using Claude? /integrate/claude is the setup page — TaskManager as a custom connector (OAuth, no token), as one claude mcp add command, or as the downloadable Claude Code plugin, which brings a skill that already knows this API and the /tm-inbox, /tm-triage, /tm-new, /tm-ticket and /tm-standup commands. The plugin's files are readable at /lib/claude-plugin/.

Install

Pick your runtime. Everything under /lib/v1/ is pinned and cached for a year; /lib/latest/ is the same build under a moving name and is never cached.

Node cannot import over https, so install the tarball — a normal dependency, which is what makes tsc and every editor resolve its types. 

npm i https://taskmanager-example.web.app/lib/v1/tm-sdk.tgz

Pin a build by using its versioned name instead:

npm i https://taskmanager-example.web.app/lib/v1/tm-sdk-1.0.0.tgz
import { createClient } from '@tm/sdk';

const tm = createClient({ token: process.env.TM_TOKEN });
console.log(await tm.me());

Import the TypeScript file and Deno types it from the real source — nothing else to configure. 

import { createClient } from 'https://taskmanager-example.web.app/lib/v1/sdk.ts';

const tm = createClient({ token: Deno.env.get('TM_TOKEN')! });
console.log(await tm.me());

Or give it a bare name in deno.json:

{
  "imports": {
    "@tm/sdk": "https://taskmanager-example.web.app/lib/v1/sdk.ts"
  }
}

Importing sdk.js works just as well: hosting sends X-TypeScript-Types: /lib/v1/sdk.d.ts and the bundle starts with /// <reference types="./sdk.d.ts" />. Deno honours either.

Bun takes the npm tarball …

bun add https://taskmanager-example.web.app/lib/v1/tm-sdk.tgz

… or the URL import, like Deno — it reads the same triple-slash reference:

import { createClient } from 'https://taskmanager-example.web.app/lib/v1/sdk.ts';

const tm = createClient({ token: Bun.env.TM_TOKEN! });
console.log(await tm.me());

No build step: the bundle is ESM with no dependencies and /lib/** is served with Access-Control-Allow-Origin: *. 

<script type="module">
  import { createClient } from 'https://taskmanager-example.web.app/lib/v1/sdk.js';

  const tm = createClient({ token: TM_TOKEN });
  console.log(await tm.me());
</script>
A board token acts as you (or as one of your agents) with its full scopes. Never ship one to a public page — the browser build is for internal tools, extensions and notebooks.

A worked example

One token means one board and one identity, so nothing below takes a board. Get a token in the app under Account › Tokens. 

import { createClient } from '@tm/sdk';

const tm = createClient({ token: process.env.TM_TOKEN });

const me = await tm.me();                       // principal, board, role, scopes
const mine = await tm.tickets.list({ assignee: 'me', state: 'active' });

// Publish the plan, then tick it off as you go.
const list = await tm.tasklists.set('ENG-42', {
  title: 'Plan',
  items: ['Read the spec', 'Write it', 'Test it'],
});
await tm.tasklists.item('ENG-42', list.id, list.items[0].id, { status: 'doing' });

// Ask a person something and wait for the answer.
const answer = await tm.questions
  .ask('ENG-42', {
    title: 'Which database?',
    fields: [{ id: 'db', label: 'Database', type: 'single', options: ['Postgres', 'SQLite'], required: true }],
  })
  .waitForAnswer({ timeoutMs: 30 * 60_000 });
answer.values.db;                               // typed from the fields you passed

// Attach the report and say so.
const report = await tm.files.upload('ENG-42', { name: 'report.html', text: html });
await tm.messages.post('ENG-42', { markdown: 'Done — see the report.', attachments: [report.id] });

The whole orchestrator

tm.work() streams the agent inbox, runs your handler per event, keeps a heartbeat alive while it runs (so the ticket says “Working …”), marks it done or error, and acks the event only after the handler returned — a crash replays it. 

await tm.work(
  async ({ ticket, beat, tm }) => {
    await beat?.update({ message: 'Reading the ticket' });
    const t = await tm.tickets.get(ticket);
    await tm.messages.post(ticket, { markdown: `On it: ${t.title}` });
  },
  { concurrency: 2, filter: ['assigned', 'mentioned'] },
);

Your own MCP server

Rather than handing an agent the whole /mcp endpoint, build the tool list you want. mcpTools() returns plain { name, description, inputSchema, handler } definitions, so they drop into any MCP server, and it silently drops the tools your token's scopes already forbid. 

import { createClient, mcpTools, registerTools } from '@tm/sdk';
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';

const tools = await mcpTools(tm, {
  only: ['get_ticket', 'post_message', 'set_tasklist', 'update_task_item', 'ask_question', 'heartbeat'],
  rename: { post_message: 'reply' },
  describe: { reply: 'Reply to the ticket you are working on. Markdown.' },
  defaults: { ticket: 'ENG-42' },   // pinned: the model never passes it and cannot change it
});

registerTools(new McpServer({ name: 'my-orch', version: '1' }), tools);

Versioning and caching

  • /lib/v1/* — Cache-Control: public, max-age=31536000, immutable. The v1 is the API's wire version, not the package's: the files under it are replaced in place on every deploy, so pin a build with the versioned tarball name when a byte-for-byte build matters.
  • /lib/latest/* — the same files, Cache-Control: no-store. Always the newest build.
  • A breaking change to the wire format gets a new prefix (/lib/v2/); /lib/v1/ keeps working.
  • Every file is served with Access-Control-Allow-Origin: *.
