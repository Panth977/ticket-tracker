Indicators and descriptions

Everything a person names — a board, a board's stage, an artifact, a memory, a workspace — carries the same two things: an indicator (the mark the sidebar, the title dropdowns, cards and every picker draw beside its name) and a description (plain text saying what it is for). Before this, boards and artifacts asked for a colour, memories for a typed emoji, boards had rich text and stages had nothing. Now there is one model, one picker, one component, and agents get a sentence of intent on everything they can list.

A · The indicator

shared/src/types/indicator.ts. Exactly one of four kinds; nothing is ever typed character by character:

kind stored drawn as
color { kind, color: '#rrggbb' } — one of INDICATOR_COLORS (14) a filled dot (small sizes) or rounded square (md and up)
icon { kind, icon, color } — icon one of INDICATOR_ICONS (≈ 90 lucide names, kebab-case), tinted with a palette colour the lucide icon in that colour
emoji { kind, emoji } — one emoji (a grapheme, ≤ 32 code units; the schema refuses anything without a pictographic code point) the emoji
image { kind, path } — indicators/{uid}/{fileId}/{name} (INDICATOR_PATH_RE) the uploaded picture, rounded, object-fit cover
  • The emoji is PICKED. The picker is a grid with categories and a search by name and keyword over a compact built-in dataset, loaded lazily; there is no text box an emoji could be typed into. The schema check is the server's half of the same rule.
  • The icon list is closed. The app maps each id to its lucide component through a static import map (frontend/src/lib/ui/indicatorIcons.ts), so the bundle holds exactly those icons, and nothing outside the list can be stored.
  • A new entity gets one: what the create call sent, else defaultIndicator(seed) — a palette colour from a stable hash of its name.
  • A tint where the app needs a colour (a stage column, a board's key chip): indicatorColor(i) — the colour of a colour or icon indicator, else the palette's first. A board's legacy color is kept equal to it on every write, so readers that still use board.color stay right.

B · Uploaded images

  • The app uploads straight to Storage (like an avatar), at indicators/{uid}/{fileId}/{name} with a fresh fileId, then stores the path in the indicator.
  • storage.rules: create only by request.auth.uid == uid (and not refused by the allow list), fileId matching [A-Za-z0-9_-]{6,64}, ≤ 1 MB (INDICATOR_IMAGE_MAX_BYTES), content type one of INDICATOR_IMAGE_TYPES (PNG, JPEG, WebP, GIF, SVG). Written once (a new picture is a new file id); the owner may delete. Read: any signed-in person — an indicator is shown to everyone who sees the entity, and the path is unguessable.
  • It is DRAWN through the file door (GET /api/files/url, which accepts indicators/… for any signed-in caller, as it does avatars), cached per path by lib/files/source until the signed URL nears expiry. Right after an upload the local object URL is used, so the new mark shows at once.
  • A command that stores an image indicator validates the path's shape; nothing ties the picture to one entity, so the same upload may mark several.

C · The description

  • Plain text (Markdown allowed), at most DESCRIPTION_MAX = 2000 characters, the same limit everywhere (artifact and memory descriptions grew from 500). Shown under the name in settings and as a tooltip or subtitle where there is room.
  • Mostly for agents. MCP and REST list them: an agent reads a board's description to know what goes there, a memory's to know what it holds, and a stage's to know when a ticket belongs in it — "Ready for QA: the build is on staging and the PR is linked" says more than the name. The MCP tool descriptions say so.
  • Boards used to hold rich text. A board's description is now string | RichText until the migration flattens it; descriptionText() (shared/src/logic/description.ts) reads either, turning a doc into Markdown. An old client that still sends a rich-text doc to boardUpdate is accepted and stored flattened.

D · Where each entity keeps them

entity indicator description legacy fields (kept, read through indicatorOf)
board boards/{b} indicator description (string; RichText before the migration) color (a name like 'blue' or hex), typed icon
stage (in board.stages[]) indicator description (optional) color
artifact artifacts/{a} indicator description emoji icon (none = the old ◆ glyph)
memory memories/{m} indicator description emoji icon (none = 🧠, MEMORY_DEFAULT_INDICATOR)
workspace users/{u}/workspaces/{w} indicator description (optional) color

indicatorOf(entity, seed, fallback?) is the one reader: the entity's own indicator, else an emoji icon, else a lucide-name icon tinted with its colour, else its colour (legacy names map through NAMED_COLORS), else fallback or a palette colour from the seed. So an old document draws the same mark before and after the migration.

E · Commands and the doors

  • Create and update take indicator and description: boardCreate / boardUpdate (patch), stages inside boardUpdate's stages patch (each validated), artifactCreate / artifactUpdate, memoryCreate / memoryUpdate (the old icon emoji is still accepted from old clients), workspaceCreate / workspaceUpdate. A bad icon id, a typed non-emoji or a path outside indicators/ is a 400.
  • Out: PublicBoard has indicator and description_md; every PublicStage has indicator and description; PublicArtifact and MemoryOut have indicator. REST (POST /v1/boards), MCP (board, artifact, memory and workspace tools) and the SDK accept and return them (SDK 1.6.0).

F · In the app

  • lib/ui/Indicator.svelte draws one (sizes xs–xl; pass the entity as of or an explicit indicator). lib/ui/IndicatorPicker.svelte is the picker — tabs Colour · Icon · Emoji · Upload: swatches, an icon grid with a tint row, the emoji grid with categories and search, and a file input that checks type and size, uploads and previews.
  • Everywhere an entity is shown or picked: the sidebar (boards, artifacts, memories, workspaces and their children), the title switchers, every dropdown and menu that lists boards, artifacts, memories, workspaces or stages (MenuItem takes an indicator), the command palette and search results, cards, the kanban column headers (with the stage description as a tooltip) and a ticket's stage chip.
  • Settings and create dialogs — board General and Stages, artifact and memory General, the workspace dialog, and New board / artifact / memory / workspace — all ask for name, description, indicator, with the same component in the same order. The free-typed icon box and the colour-only input are gone.

G · The migration

scripts/migrate-indicators.mjs (logic in scripts/lib/indicators.mjs; unit-tested in qaqc/test/migrate-indicators.test.ts, emulator-tested in qaqc/rules/migrate-indicators.test.ts):

  • every board: indicator = indicatorOf(board) when missing (a board with no usable colour gets color = indicatorColor(…)); a rich-text description → plain text; every stage without one gets indicatorOf(stage) — stage descriptions stay absent;
  • every artifact: its emoji, else a palette colour; every memory: its emoji, else 🧠; every workspace: its colour.

Nothing legacy is removed. Dry run by default; idempotent (a document that already has its indicator plans nothing). 

pnpm --filter @tm/shared build
node scripts/migrate-indicators.mjs --project <id>            # dry run
node scripts/migrate-indicators.mjs --project <id> --apply    # write

Credentials as for the other migrations: application-default, TM_GCLOUD_ACCOUNT=<you@…>, or the emulator with FIRESTORE_EMULATOR_HOST.
