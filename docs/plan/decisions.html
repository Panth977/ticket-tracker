Architecture Decisions Roadmap Agents SDK Review From TeamTrack Run

Decisions

These are the choices that are expensive to reverse. Each one lists the alternative that was turned down and why. If you disagree with one, leave a note on the card it touches (App or Platform tab, Comment in the bottom right) so it gets argued before it gets built.

D1 · Writes through commands, not client writes

ChosenClients read Firestore directly. Every write is a POST to /api/{command}, and rules deny writes except for a person's own pointers.
RejectedClients write Firestore under rules, and triggers do the side effects.
WhyNearly every write has a second document to keep in step: the key counter, activity, the other end of a link, notifications, webhooks. Rules cannot express "a commenter may change stageId only between the stages in their grant, and only on tickets assigned to them" in a way that can be maintained. REST and MCP need the same logic anyway. With client writes, every rule would exist twice, once in firestore.rules and once in the API, and the two would drift.
CostA write takes about 150–400 ms instead of about 50 ms. Optimistic updates hide this. Cold starts are covered by minInstances: 1 on api in production.

D2 · One function, four doors

ChosenOne 2nd-gen HTTPS function api (Hono router) that serves /api, /v1, /mcp, /oauth and /hooks.
RejectedOne Cloud Function per endpoint, or a separate Cloud Run service for MCP.
WhySixty functions means sixty cold starts, sixty deploy units and sixty minimum-instance bills. One service with concurrency 80 stays warm on the traffic from the app alone, so REST and MCP calls ride on warm instances. It can still be split later along the door boundaries, which are already separate files.

D3 · Tickets as a subcollection of their board

Chosenboards/{b}/tickets/{t}, plus a collection-group query for My Work
RejectedTop-level tickets with a boardId field.
WhyA top-level collection needs a rule that get()s the ticket's board, and a list query cannot prove that per document. The query would have to filter on boardId anyway. With a subcollection, the board is in the path, so the rule is one get(). For the collection group, the rule auth.uid in resource.data.assigneeUids follows from the query itself.
CostA ticket cannot move between boards — there is no transfer feature (dropped by decision D13). Relate tickets across boards with a link or a #reference instead.

D4 · The ticket id is not the ticket key

ChosenA generated immutable ticketId, a key field, and a keys index that keeps old keys as redirects
RejectedThe key as the document id, which is what TeamTrack does with TICKET_ID.
WhyKeys change when a ticket moves. Links in emails, WhatsApp messages, GitHub PRs and other tickets' #refs must keep working after that.

D5 · Load the board, compute the view in the browser

ChosenOne live query per board over its active tickets. Filter, sort, group-by and swimlanes are pure functions in packages/shared.
RejectedOne Firestore query per view.
WhyFirestore cannot OR across fields, cannot filter on range and inequality over two fields, and needs a composite index for every combination. User-defined views with custom fields would need thousands of indexes. In the browser, switching views is instant and costs no reads.
CeilingAbout 5,000 active tickets per board, or about 5 MB. Past that, a board is flagged large and views run through Typesense (filterable on every field) with paging. Archived tickets are never loaded by default.

D6 · Rich text is ProseMirror JSON, not Markdown or HTML

ChosenThe TipTap document is stored as-is. The server derives text, mentions and refs and validates it against the schema.
RejectedMarkdown, which TeamTrack used, or sanitised HTML.
WhyMentions and ticket references become typed nodes with ids, so renames do not break them. There is no parser disagreement between the editor and the renderer, and no HTML to sanitise. Markdown remains the exchange format at the edges (REST, MCP, email) and is converted on the way in and out.

D7 · Notifications: inbox now, channels queued

ChosenThe inbox row is written after commit. Channel delivery goes through Cloud Tasks with a per-minute dedupe key, and each attempt is logged in deliveries.
RejectedSending from the handler, as TeamTrack did, or a Firestore outbox collection with a trigger.
WhyCloud Tasks gives retries, rate limits per provider, delayed delivery (for quiet hours) and deduplication by task name. These are the four things an outbox trigger would have to reimplement. The one-minute window is what turns five comments into one push.

D8 · Search is Typesense

ChosenTypesense (Cloud to start; self-hosted on a small VM if cost matters), synced by onTicketWritten, queried from the browser with per-user scoped keys
AlternativesAlgolia, which is the same shape but costs more per record. Firestore keywords[] arrays can do prefix search on title words only. Vertex AI Search is too heavy.
WhyThe # picker and ⌘K need prefix search on any word and infix search on keys (42 should find ENG-42). A scoped key embeds a boardId:[…] filter, so the browser can never see results from boards it cannot read.

D9 · MCP on OAuth, not API keys

ChosenOAuth 2.1 with PKCE, dynamic client registration, and protected-resource metadata, as the MCP authorization spec expects
RejectedPasting an API key into the MCP client.
WhyThis is the only way a person adds the server with one URL and a consent click, in Claude and other clients. The grant is per person, can be revoked in Account › Connected apps, and every change it makes is attributed via MCP. API keys still work for MCP in headless setups.

D10 · Roles belong to people, not teams

Chosenadmin · editor · commenter · viewer, granted to each person on each board, plus a per-person StageGrant. Tickets are assigned to people. Invites are to people.
RejectedTeamTrack's model: a team owns a board, other teams are invited, roles come from team membership, and per-team {create, edit, status, delete} flags adjust them. Assignment was to a team or to "Team > email".
WhyTeams were an indirection between a person and what they may do. Changing one person meant changing a team, and the privilege flags existed to undo that. With one role per person per board there is nothing to union, can() is a single lookup, a rename cascades nowhere, and "who can see this board" is a list you can read. If groups are ever needed, they can come back later as a way to add many people at once, never as a holder of roles.

D11 · Presence and typing in the Realtime Database

ChosenRTDB presence/ and typing/ with onDisconnect()
WhyFirestore has no disconnect hook. A 30-second heartbeat per open tab written to Firestore would be most of the bill.

D11a · The board is everything: no workspace, no organisation

ChosenOpen sign-up. Anyone creates boards and invites people to a board by email with a role. There are no app-level roles, no directory and no settings document. Board keys are claimed app-wide.
RejectedMulti-tenant workspaces (workspaces/{ws}/…), and a single organisation with an owner and app roles (config/org, members/{uid}).
WhyThis is a personal tool. The unit people share is a board, so that is the only boundary. A workspace adds a path prefix and a tenant check to every rule. An organisation layer adds a second role nobody needs. With neither, there is one role per person per board, and can() is one lookup.
CostThere is no company-wide directory: @ only finds people on the same board, which is also a privacy property. Board keys can collide between strangers, so the second person to want ENG has to pick another key.

D14 · Cancel deletes; there is no "cancelled" state

ChosenA ticket is active or archived. The ⋯ menu offers Archive (reversible, out of the way) and Delete (permanent, one confirmation, no reason). The per-board "allow permanent delete" setting stays, so a board can offer Archive only.
RejectedThe reference tracker's third state, cancelled — read-only, hidden by default, with an optional reason recorded in the activity and the notification.
WhyAsked for directly, and correct: archive already means "keep it, out of the way". A second read-only state meant the same thing with a different word, and the reason it recorded was written onto a ticket nobody was going to open. Keep it, park it, or it is gone.
NoteA board may still have a stage in the cancelled category (a "Won't do" column). That is where the work stands on the board, which is a different question from whether the ticket exists.

D13 · No moving a ticket between boards

ChosenA ticket lives on the board it was created on. To connect work on another board, link the tickets or #reference them.
RejectedTransfer (copy the ticket, its thread, activity and files to another board, re-key it and redirect the old key), which the reference tracker had and phase 1 built.
WhyAsked for directly: it is machinery — option mapping per field, dropped assignees, a queued copy job, key redirects — for something that happens rarely in a personal tool, and it is the most dangerous write in the system.
CostA ticket filed on the wrong board has to be closed and filed again; the new one can reference the old.

D12 · Email: Resend. WhatsApp: Meta Cloud API directly.

ChosenResend for outbound mail and inbound parse. Meta's WhatsApp Cloud API, without a BSP.
AlternativesSendGrid or SES (both are fine; the provider sits behind a sendEmail() port). Twilio or Gupshup for WhatsApp, which add a markup and a second dashboard.
Watch outWhatsApp templates must be approved before launch, need a verified business, and every message outside the 24-hour window is billed. That is why WhatsApp is strictly opt-in and limited to deadline and assignment events by default.
