The SDK

Everything Agents · §M promised, as it was built: the package in sdk/, the artefacts hosted at /lib/**, every method on the client, the orchestrator loop, the MCP tool factory, and the versioning and cache rules that let a URL import be typed and still be fast.

Writing a client by hand for every orchestrator is the thing this app exists to avoid. So the app ships one: a small, typed, dependency-free JavaScript SDK, hosted next to the API it talks to, that turns every /v1 route and every MCP tool into a function. Its types come from the same @tm/shared schemas the server validates with, so a wrong field is a compile error rather than a 400.

Where it lives

https://taskmanager-example.web.app/lib/       the install page: a tab per runtime, examples
   /lib/v1/sdk.js           ESM bundle, no dependencies   (browsers, Deno, Bun)
   /lib/v1/sdk.min.js       the same, minified
   /lib/v1/sdk.ts           the whole SDK as ONE TypeScript file (Deno and Bun type it natively)
   /lib/v1/sdk.d.ts         one flat declaration file — no imports, so a URL import can use it
   /lib/v1/tm-sdk-1.0.0.tgz   and   tm-sdk.tgz     npm install, for Node
   /lib/v1/openapi.json     OpenAPI 3.1 for /v1, as of this build
   /lib/v1/sdk.json         what this build is: version, byte sizes, SHA-256 of every file
   /lib/latest/…            the same eight files, never cached

The v1 is the API's wire version, not the package's. A breaking change to the wire format gets a new prefix (/lib/v2/) and /lib/v1/ keeps working; a new SDK build for the same wire version replaces the files in place and arrives under a new tarball name.

One source, five artefacts

sdk/build.mjs concatenates sdk/src/*.ts into one file with the local imports stripped, and derives everything else from that:

sdk/src/*.ts  ──concat, imports stripped──▶  dist/sdk.ts
                                                │
                     tsc --emitDeclarationOnly  │        esbuild
                                                ▼            ▼
                                          dist/sdk.d.ts   dist/sdk.js + sdk.min.js
                                                             │  npm pack
                                                             ▼
                                                   dist/tm-sdk-<version>.tgz

Concatenating first is what makes the whole promise cheap to keep. The declaration file is emitted from a file that has no imports, so it cannot come out mentioning @tm/shared or zod — which a URL import could never resolve — and sdk.ts is the very thing that was type-checked and bundled, not a second copy that drifts. The build then imports every artefact and calls it before it will write a tarball.

The client

import { createClient } from '@tm/sdk'

The token names one board and one identity — it acts as you, or as one of your agents — so nothing on the client takes a board. What it may do is its scopes ∩ the role of the principal it acts as; the server decides, the SDK never guesses.

The beat is what puts 🟢 Working · "Running tests" on the ticket, and it is why heartbeat.start() returns a handle rather than a promise:

const beat = tm.heartbeat.start({ ticket: 'ENG-42', message: 'Running tests' })
beat.update({ message: 'Writing the report', progress: 0.8 })   // and sends one right away
await beat.done()            // or beat.error('the build failed') — the UI stops saying "working"

Beats go out every 60 s and the app calls an agent stale after 75 s of silence (§L), so everyMs is a knob you should rarely turn.

Errors, retries, idempotency

Everything that fails throws TmError: a code ('invalid', 'unauthenticated', 'forbidden', 'not_found', 'conflict', 'gone', 'too_large', 'unprocessable', 'rate_limited', 'internal', 'unavailable', 'timeout', 'network'), the HTTP status, and the whole RFC 9457 problem+json body. isTmError(e) narrows it.

  • 429, 5xx and network failures retry with exponential backoff and jitter, and honour Retry-After.
  • Every write carries an Idempotency-Key, generated once per call and reused across that call's retries — so a retried create is still one ticket. Pass your own in o.idempotencyKey to make a retry across process restarts safe too.
  • 4xx other than 429 never retries: the request was wrong and will stay wrong.

The orchestrator loop

The loop every orchestrator would otherwise write by hand:

stream the inbox  →  run the handler for each event  →  keep a heartbeat alive on that
ticket while it runs  →  mark it done (or error, with the message)  →  ack the event,
but only once the handler returned
await tm.work(
  async ({ event, ticket, tm, beat, signal }) => {
    await beat?.update({ message: 'Reading the ticket' })
    const t = await tm.tickets.get(ticket!)
    await tm.messages.post(ticket!, { markdown: `On it: ${t.title}` })
  },
  { concurrency: 2, filter: ['assigned', 'mentioned'] },
)
OptionDefault
concurrency1How many events may be in flight at once.
filtereverythingA list of EventTypes, or a predicate.
heartbeatonfalse for a token without status:write; otherwise { everyMs, message }.
onErrorlog and carry onCalled when a handler throws.
max—Stop after this many events: one-shot runs and tests.
acktrueAck handled events.

Two decisions in there are worth keeping in mind:

  • Acking last. A crash mid-handler leaves the event unacked, so the next run picks it up again. The cost is that a handler must tolerate being run twice for one event; the benefit is that nothing is ever silently dropped, which is the failure you cannot debug afterwards.
  • Never two handlers on one ticket. Whatever concurrency says, two events for the same ticket are serialised — two handlers editing one task list would race, and the second event is usually about the first one's own work.

It resolves with { handled, failed, cursor }, so a caller can resume somewhere else.

The MCP tool factory

Rather than handing an agent the whole /mcp endpoint, an orchestrator builds the tool list it wants. mcpTools() returns plain data — { name, description, inputSchema, handler, scopes, readOnly, originalName }, a JSON Schema and no zod — so it drops into any MCP server, not just the official SDK.

import { createClient, mcpTools, registerTools } from '…/lib/v1/sdk.js'
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js'

const tools = await mcpTools(tm, {
  only: ['get_ticket', 'post_message', 'set_tasklist', 'update_task_item', 'ask_question', 'heartbeat'],
  exclude: ['delete_tasklist'],
  rename: { post_message: 'reply' },
  describe: { reply: 'Reply to the ticket you are working on. Markdown.' },
  defaults: { ticket: 'ENG-42' },
  wrap: { reply: (call) => async (args) => call({ ...args, markdown: prefix + args.markdown }) },
})

registerTools(new McpServer({ name: 'my-orch', version: '1' }), tools)
OptionKeyed by
only · excludethe original nameWhich of the 24 tools to keep.
renamethe original name{ post_message: 'reply' } — what the model sees it called.
describethe name the model seesYour words instead of the published description.
defaultsargument nameArguments the model never passes and cannot change. ticket also fills the key argument, since most tools call it that.
wrapthe name the model seesA middleware around the call — prefix the text, count the calls, refuse one.
scopes—Skip the GET /v1/me it would otherwise do to learn them.
skipScopeFilter—Keep every tool, whatever the scopes say.

Two things it does quietly. It drops the tools the token's scopes already forbid, so a model is never offered something that must fail — the server still checks, of course; the filter is about not wasting a turn on a refusal. And each tool's name, description, input schema and scopes are the same ones /mcp publishes from shared/api/mcp.ts: sdk/test/mcp.test.ts compares the two lists item by item, so they cannot drift apart.

registerTools() is the convenience for the official SDK. Call it before connect(), and do not mix it with that server's own registerTool().

Versioning and cache rules

Hosting sends these, from firebase.json, on everything under /lib/:

PathHeaderWhy
/lib/v1/**Cache-Control: public, max-age=31536000, immutable What a lockfile and an editor's cache point at. A year, and no revalidation: a URL import in a hot loop must not cost a round trip.
/lib/latest/**Cache-Control: no-store A moving name is only useful if it moves. Nothing may keep a copy.
/lib/Cache-Control: no-cacheThe install page changes with the docs; revalidate every time.
/lib/**/*.tsContent-Type: application/typescript; charset=utf-8 Hosting would otherwise call a .ts file video/mp2t — an MPEG transport stream — and Deno would refuse it. One rule covers .d.ts, which also ends in .ts.
/lib/**/*.jsContent-Type: text/javascript; charset=utf-8
/lib/**/*.tgzContent-Type: application/gzipnpm is happier with the real type than with application/octet-stream.
/lib/**Access-Control-Allow-Origin: *
X-Content-Type-Options: nosniff
Cross-Origin-Resource-Policy: cross-origin		 Everything here exists to be fetched from somewhere else. Nothing under /lib is private — it is the same bundle every consumer already has.
/lib/v1/sdk*.jsX-TypeScript-Types: /lib/v1/sdk.d.ts The one that makes import … from 'https://…/sdk.js' typed in Deno. Absolute, so it resolves the same from any importing module; /lib/latest/ points at its own copy.
Header rules match the request path, not the file. /lib/index.html does not match a request for /lib/, which is what people actually type — so the install page's rule is spelled three ways (/lib, /lib/, /lib/index.html). This is the kind of thing that looks right in review and is wrong in production, which is why it is asserted rather than argued.

The page you point an agent at

The SDK is for the person writing the orchestrator. The thing you hand the orchestrator itself is Agents · §O: one URL that teaches it the whole software, generated from the same sources so it cannot drift.

The zip is written by the same generator, STORE-only and stamped from the changelog date, so it is byte-stable and the deploy guard can compare it.

scripts/gen-integration.mjs builds all of them: the prose lives in scripts/integration-source/*.md (with the Claude guide in integrate-claude.md and the plugin's own files under claude-plugin/) with {{gen:…}} markers, and everything else is read from the OpenAPI document, the MCP tool registry in @tm/shared, the shared contracts and sdk/dist/sdk.d.ts — the SDK surface is copied out of the declaration file verbatim, because a paraphrase is a second copy and a second copy rots.

It is deterministic, which is what lets the deploy guard it the way the SDK artefacts are guarded: the same inputs produce the same bytes, every list is emitted in a fixed order, and nothing reads the clock. The "updated" stamp is the date of the newest changelog entry, not new Date() — a wall-clock stamp would fail the guard every midnight for no reason. The changelog's top entry must also match the SDK's version, so a release cannot ship without saying what changed.

pnpm integrate:gen        regenerate every published file (and the plugin zip)
pnpm integrate:check      fail if the committed copy is stale (what the deploy runs)
pnpm build                builds everything, then regenerates

Hosting serves the .txt files as text/plain; charset=utf-8, with Cache-Control: no-store on /llms*.txt and /integrate.json — an agent re-reading the page is asking whether its knowledge is current, and a cached answer defeats the question — and Access-Control-Allow-Origin: * throughout, since an agent fetches it from anywhere. scripts/deploy-lib-check.mjs asserts all of that against the real hosting emulator, along with the fact that /llms-full.txt really does contain every REST path and every MCP tool name.

How it gets there

pnpm deploy:prod, in order:

  1. check frontend/.env.production
  2. build the SPA — which copies frontend/static/lib/index.html to frontend/build/lib/
  3. package the functions and simulate Cloud Build on them
  4. scripts/deploy-lib.mjs: stage sdk/dist into frontend/build/lib/{v1,latest}/, and generate openapi.json
  5. scripts/gen-integration.mjs: refuse a stale committed copy of the integration context, then stage a copy carrying this project's URLs into frontend/build/
  6. firebase deploy --config firebase.deploy.json

Step 4 comes after step 3 on purpose: openapi.json is generated by importing the backend that was just built (the document is a pure function of the zod schemas, and API_URL is the only thing it takes from a request), so what /lib ships describes what /v1 will serve.

It refuses to ship a stale SDK. Every artefact must exist, be stamped with the version sdk/package.json claims, start with the triple-slash reference, have a flat declaration file, and be newer than every source under sdk/src — otherwise the deploy stops and says to run pnpm sdk:build. A deploy that silently shipped yesterday's bundle next to today's API is the exact failure this plumbing exists to prevent.

And the headers are checked rather than believed:

node scripts/lock.mjs emulators -- node scripts/deploy-lib-check.mjs

starts the real hosting emulator on the real config and fetches all eighteen files, asserting the content type, the cache rule, the CORS header and X-TypeScript-Types on each, plus the bytes themselves — the bundle's reference line, the gzip magic number, that openapi.json parses — and that firebase.deploy.json still carries the same header block. It does the same for the four integration-context URLs.
