Architecture

A private, multi-board ticket tracker, on Firebase with a Svelte front end. Anyone can sign up and create boards, and the board is the only boundary: you invite people to it by email. It has custom fields, saved views, deadlines, ticket keys and linked tickets. Every ticket has a full conversation thread with @people, #tickets, pins, and attachments. Notifications go out in the app, as browser push, by email, and on WhatsApp. The same operations are open to scripts over REST and to AI agents over MCP. This page describes the design end to end. The App and Platform tabs define every collection, function, and screen it mentions.

The shape of it

There are three rules. Everything else on this page follows from them.

  1. Reads go straight to Firestore, live. The Svelte app subscribes with onSnapshot and security rules decide what it can see. This is how a card moves on everyone's screen as it is dragged, which TeamTrack could not do: it refetched on focus and two seconds after your own edit.
  2. Writes go through one command layer. Clients never write Firestore directly. The only exceptions are a person's own read pointers, devices and inbox flags. Every mutation is a function in functions/src/commands. The Svelte app, REST, MCP and the inbound hooks all call the same functions. Nearly every write has a second thing to keep in step: the key counter, the activity row, the the other end of a link or reference, notifications, webhooks, the search index. That logic is written once.
  3. Side effects are queued, not awaited. A command commits its transaction and returns. It then enqueues delivery and webhooks on Cloud Tasks, which retries, rate-limits and deduplicates them. TeamTrack fired email from inside the request handler, so a slow mail server slowed the request and a crash lost the mail.

The board is everything

There is nothing above a board. There is no workspace, no organisation, no app-wide role and no directory. Anyone can sign up. Anyone can create a board and becomes its admin. The admin invites people by email with a role. Once someone accepts, they are on that board: they can be assigned tickets, @mentioned and notified there, and nowhere else. A person's boards are exactly the ones they created or accepted.

LayerRolesWhat it decides
Boardadmin · editor · commenter · viewerEverything. Each person has their own role on each board. An admin invites, removes and re-roles people; editors create and edit; commenters talk and move tickets within their per-person StageGrant; viewers read.
Token scopeScopeOnly narrows. An API token or MCP grant can never do more than the principal it acts as — the person, or (phase 2) the agent, whose own board role can() checks: scopes ∩ can().

A board holds access: { [uid]: BoardRole }, which is the authority the rules read, and readerUids, its keys, because Firestore can only prove a list query with array-contains. So "my boards" is where(readerUids, array-contains, me), and every rule is one get() on the board. boards/{b}/members shows the same people for display: the @mention list and the assignee picker. Invites sit at the top level, because an invitee has to see "what have I been invited to" before they can read the board. Write permissions are enforced in can(): one lookup, board.access[uid], with a unit test for every branch.

Board keys like ENG are claimed across the whole app, first come first served (boardKeys), the same way a username is. That is what lets #ENG-42 and /t/ENG-42 mean one ticket without saying whose board it is.

Stored as a uid, shown as a name and an email. There are no handles or usernames. Every assignee, mention, author, role and read pointer is a uid. On screen a person is their display name and email, with their profile picture. The @ picker matches either the name or the email, and two people named Priya are told apart by the email under each name. Both are looked up from the uid, so a rename shows up everywhere at once.

TeamTrack keyed assignees, read pointers and notification prefs by email address, and assigned work to teams ("Team > a@b.com"). A change of address was a data migration, and a team rename cascaded across every ticket. Here an assignee is a uid, a role belongs to a uid, and an email is only a contact detail on users/{uid}.

Tickets are a subcollection of their board. The board screen reads a single collection, and its rule needs a single get(). My work uses a collection-group query, where(assigneeUids, array-contains, me), and its rule can be proven from the query alone. See tickets for the indexes.

Threads, mentions and attachments

A message body is a RichText: the editor's JSON document, plus three fields the server derives from it: plain text, mentions (uids) and refs (ticketIds). A mention is a node that carries a uid and renders the person's current display name, so renaming someone never breaks it. TeamTrack stored [@Name](mailto:…) links in Markdown.

  • @ searches the people on the board. A mentioned person is always notified, whatever their board preference.
  • # searches Typesense by key and by title words, so #login finds ENG-42. The linked ticket gets a system line saying it was mentioned in ENG-40.
  • Pin is available to editors and above. Pins float at the top of the thread, and pinning writes a system line, because a pin records a decision.
  • Attachments upload straight to Storage while you type, then the message names their paths. Images get a WebP thumbnail. The limit is 50 MB per file. An upload that is never attached is removed after 24 hours.
  • Formatting: bold, italic, strike, code, code blocks, lists, checklists, quotes, links and headings. There is no raw HTML. Markdown from REST, MCP or email is converted into the same document on the way in; since phase 2 the Markdown source is kept too, and the thread renders it as GitHub-flavoured Markdown.
  • Files agents write (phase 2): an agent uploads plan.md or report.html as text, then names the file in its message. Every file opens natively in the File viewer; HTML runs in sandbox="allow-scripts allow-popups allow-forms", never with allow-same-origin.

Custom fields and views

Field definitions live on the board, and values live on each ticket under the field's id. Renaming a field rewrites one definition and no tickets. Removing a field archives it and keeps the values. A stage can require fields before a ticket may enter it. This is TeamTrack's "no Done without a Solution" rule, now general and enforced on the server.

A view is data: type, a filter tree with and/or groups and tokens like me and thisWeek, sort, group-by, swimlanes, columns and date fields. Views are personal or shared. TeamTrack had a views key that nothing read, and kept table layout in each browser's localStorage.

Notifications

Each person decides, from their own profile. Account › Notifications holds a grid of event × channel (in app, push, email, WhatsApp), quiet hours, the digest, and how long before a due date to be reminded. Account › Channels is where you enable push on a browser and link a WhatsApp number. The only per-board choice is also yours: the 🔔 on a board's bar sets Everything / Mine / Muted. No board and no admin can turn a channel on or off for someone else. TeamTrack's owner-managed mode is gone.

Email and WhatsApp are two-way. Replying to a notification email posts to the thread, and so does replying on WhatsApp. Both are attributed via email / via whatsapp. deadlineSweep and digestSend are the only notifications that no person's action causes.

The platform: REST, webhooks, MCP

  • REST (/v1): resources named by key (/v1/tickets/ENG-42) and fields named by name. It has an Idempotency-Key header, problem+json errors, and cursor pagination. The OpenAPI document is generated from the same zod schemas the commands validate with.
  • Auth: tokens, stored hashed and shown once. Since phase 2 each token is for exactly one board and acts either as you or as one of your agents on that board; its changes read "Panth via token <name>" or "Builder (agent) via token <name>". Third-party apps use OAuth 2.1.
  • Webhooks: signed with HMAC(secret, t.body), retried 8 times over about 24 hours, and disabled after 20 consecutive failures. Every attempt is visible in settings.
  • MCP: a stateless Streamable HTTP server at /mcp. Discovery, dynamic client registration and PKCE follow the MCP authorization spec, so a person adds one URL and approves. The tools are read and write with no delete. Every change shows as "Panth via Claude (MCP)".
  • Intake: TeamTrack's reporting API, kept. A board can take tickets from a website widget using a slug and secret with rate limits, or by email-to-board. The secret is now hashed.
  • Integrations: GitHub (a key in a branch or PR links it and a merge can move it), Slack (a board activity channel), and a calendar subscription (a read-only ICS feed of your deadlines).
