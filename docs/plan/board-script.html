Board script

A board's ticket fields and filters, written as code. Panth (ORCH-35, 2026-11-03): "there are too many fields in board and ticket out of the box … we only need {Stage, Assignees} … all fields are code generated instead of this GUI … user can build any kind of form." Out of the box a ticket now has Stage and Assignees; everything else on its Details pane, and every filter above the board, is the board's script. The reference an author reads is §10 of /integrate (also get_template_docs); this page is why it is built the way it is.

A · The thing

  • One per board: the template boards/{b}/templates/script with kind: 'script' (SCRIPT_TEMPLATE_ID). templateSave always writes a script there, and no other kind may take the id. Admins write it; the board reads it.
  • A class (or a plain object) of hooks: filters, filterRender, onFilter, onSort, fieldRender, onFieldChange. Only fieldRender is required.
  • Named arguments everywhere (Panth's comment on the decisions): every hook takes one object (fieldRender({ ticket, me, board })), and so does every ui.* control and every this.api.* call. The first template API's positional forms still work for templates written before.
  • Stage is never in it. The app draws Stage above the script's fields, with the board's stage grants, requires and stage rules unchanged. Links stay the app's too (they are not a field).

B · Where it runs

  • In the template worker (templates §B): an opaque-origin Worker, as the person looking, with the watchdog. One worker per board and code version (frontend/src/lib/templates/script.ts, acquireScriptHost), shared by the board screen and every open ticket of that board.
  • The page calls a hook with one message ({ type: 'script', op, args }) and checks every answer before using it: controls against ScriptControlsSchema, a patch against ScriptPatchSchema. onFilter and onSort for a whole board are one message (apply), not one per ticket.
  • Browser only (decision 1). The REST API, MCP agents and the orch write tickets without the script; the server checks those writes the way it always did. Running onFieldChange on the server for every write (the gVisor sandbox gateway) would be a second phase.

C · Fields: what the script draws and writes

  • fieldRender returns ui.* controls: text, longText, number, toggle, select, multiSelect, people, date, dateRange and note. The app draws them with its own pickers (ScriptControls.svelte), so they look native and work on a phone. Text and numbers change on blur or Enter, never per key.
  • onFieldChange returns a ticket patch (assigneeUids, priorityId, tagIds, startAt, dueAt, dueAllDay, estimate, commitments, title, fields). The app sends it as an ordinary ticketUpdate by the viewer. One edit may write several things (the three-assignee example keeps assigneeUids the union).
  • The script's own values live in ticket.fields under a key it chooses (SCRIPT_FIELD_KEY: a letter, then up to 39 letters, digits or _, never f_…), next to the settings-defined fields' f_xxxxxx ids. The server keeps them small and plain (checkScriptFieldValue): text ≤ 10 000 characters, lists ≤ 200 short items, numbers, booleans, date ranges. REST and MCP show them under the same keys, and accept them by key.
  • A person without edit rights sees every control disabled whatever the script says. Removing an assignee also clears their commitment, as before.

D · Filters and sort

  • filterRender fills the board's Filter popover; onFilter runs for every ticket even when nothing is set (so "only my tickets" can be the default). A person's filter values are kept per board in their browser.
  • Saved views keep their sort, grouping and columns; the filter builder is gone and a saved view's old filter is no longer applied (decision 4). The search box still adds to the script's filter.
  • onSort, when the script has one, replaces the view's sort (applyView(…, { order })). It must answer at once (no async).
  • Not access control (decision 2, later): anyone on the board can still open a hidden ticket by key, search it or read it over the API. A ticket-level readers list enforced by the rules would be the way to do that.

E · Old boards and new boards

  • New boards: boardCreate saves DEFAULT_BOARD_SCRIPT (Assignees with commitments, "Only mine" and an Assignee filter). Copying a board copies its script.
  • Boards from before (decision 3): a board with no saved script runs generateBoardScript(board): priority, assignees, start, due, estimate, tags and every settings-defined field it can draw, plus filters for the same. Nothing they showed disappears, no data moves, and no migration runs. Saving in Settings › Script keeps it. Options are read from the board at run time, so renaming a priority needs no code change.
  • Settings › Custom fields, Priorities and Tags are gone (their URLs lead to Script; Panth, 2026-11-03: "all is done from code, so remove those tabs"). The generated script writes their option lists into the code. The stored definitions stay on the board for the required-field checks, the cards' chips and the table columns; priorityId / tagIds still only take values the board already had, so a new list of values goes in the ticket's own fields.

F · Not in v1

  • Running the script on the server (agents and the API bypass it).
  • Per-ticket visibility.
  • A script for the cards, the table columns or New ticket's form (card and ticket templates still do those).
  • Versions / history of the script (the editor saves over).
