Aggregates

An aggregate field is a number a board adds up: per ticket, for the board's lifetime, and per day, week or month. Cost was the first one (agents.html §Y): every turn receipt added its price to the ticket, the board and the day. Nothing about that is specific to money, so the concept is now general — hours spent, kilometres driven, story points, bugs found — and Cost is one aggregate field among any the board defines. A number enters the totals the way everything else enters a ticket: as a message in its thread.

A · The field

  • Defined in board settings › Aggregates, stored on the board as aggFields: [{ id, label, unit, period, position, showOnCard?, archived? }] (≤ 20; @tm/shared AggFieldDefSchema).
  • label (1–40) is what people read — Cost, Time. unit (≤ 12) is drawn with every value: a currency symbol before the number ($1.24), anything else after it (2.5 h), nothing for a plain count (formatAgg).
  • period is daily | weekly | monthly: the bucket the field's totals are kept in (§C). It is what Analytics draws one bar per.
  • showOnCard draws the ticket's total as a chip on its card, and the lifetime total on the board bar.
  • Ids are immutable. A new field gets a_ + 6 characters; the field turn receipts land on keeps the id cost, and only that field may carry it.
  • Removing archives. Like custom fields, a field missing from the list the editor saves is kept with archived: true: its history stays in every counter, it takes no new entries, and the editor hides it. A board starts with one field: Cost (COST_AGG_FIELD: $, daily, on cards).
  • The period locks once the field has an entry (board.aggs[id].count > 0): the buckets already written are cut by the old period and would not add up with the new ones. Label, unit, order and showOnCard stay editable. To count something by another period, add a new field.
  • Only a board admin edits the list; everyone on the board sees it.

B · An entry is a message

  • A message of kind agg — the way a question is kind question — carrying agg: { entries: [{ fieldId, value }] }: 1–10 entries, one per field. value is any finite number with |value| ≤ 1012; a negative value takes away.
  • Every field must exist on the board and not be archived, or the post is a 400 on agg. Who may comment may add entries.
  • The body is optional. Without one the server writes a short line from the entries — +$1.24 Cost · −2 h Time — so notifications, e-mail and search have text. With one (the composer's note), the note is the body.
  • Never edited, never deleted. A total is the sum of its entries; changing one in place would silently rewrite every period it fell in. A mistake is corrected by another entry (−0.5 h). messageEdit refuses an agg message like a system message.
  • A turn receipt counts too. A message with run stays a receipt (kind comment, drawn as a receipt row); when the board has an active field cost, the server adds the entry { fieldId: 'cost', value: run.costUsd } and stores it as the receipt's agg. A receipt may carry other entries as well, but not one naming cost (400).
  • In the app: the composer's Add to a total button (or /agg) opens a small dialog, one number per active field and an optional note. The thread draws an agg message as a compact row — +2.5 h Time · Asha · 14:02 — that stands alone like a receipt.

C · Where the totals live

Where What
ticket.aggs per field { total, count } for that ticket (the card chips, the drawer header)
board.aggs per field { total, count } for the board's lifetime (the board bar)
boards/{b}/aggStats/{period}:{key} one document per bucket — daily:2026-10-05, weekly:2026-W41, monthly:2026-10 — { period, key, fields: { [fieldId]: { total, count, tickets: { [KEY]: { total, count } } } }, updatedAt }. Fields that share a period share the document.
  • One transaction. messagePost writes the message, adds every entry to the ticket's and the board's counter, and to the bucket of each field's period — one read per distinct period, so a post touching three daily fields reads one stats document. Nothing is scanned and nothing is triggered.
  • The clock is the owner's: periods are cut in Asia/Kolkata (AGG_TZ), weeks are ISO weeks starting Monday (aggPeriodKey). Keys sort as strings within a period, so a range is key >= from.
  • Totals are rounded to 6 decimals on every add (roundAgg), so float drift never shows.
  • A replay counts once. A retried post (same clientId) returns the first message before anything is added.
  • Legacy mirrors. ticket.cost / board.cost ({ usd, runs }) and boards/{b}/stats/{day} are still written for every entry on cost, so an old client and the public cost fields keep working. New readers use aggs and aggStats.
  • Rules: aggStats is readable by anyone who can read the board and written only by the command layer.

D · Seeing it

  • Card: one chip per showOnCard field with a non-zero ticket total (Cost: $1.24 · 3 entries on hover). Drawer header: every active field's ticket total. Board bar: the lifetime chips of the showOnCard fields, each a link to Analytics. Boards home: the tile shows Cost (or the first card field).
  • Analytics (board settings › Analytics) picks a field — the first active one by default — and draws its buckets: 30 / 90 days, 12 / 26 weeks or 6 / 12 months by the field's period, an empty bucket an empty slot. Under the chart, the table of buckets and the tickets of the range ranked by their total. The lifetime figure is board.aggs. It reads aggStats live (period == field.period, key >= from).

E · From outside

  • Reading: PublicBoard has agg_fields ([{ id, label, unit, period, show_on_card, archived }]) and aggs ({ [field_id]: { total, count } }); PublicTicket has aggs; PublicMessage has agg: { entries: [{ field_id, value }] } | null and kind agg. The old cost fields stay, computed from aggs.cost.
  • Posting: POST /v1/tickets/{KEY}/messages, MCP post_message and the SDK's tm.messages.post take agg: { entries: [{ field_id | field, value }] } — field is the label, case-insensitive, resolved on the server. body may be omitted.
  • The buckets: GET /v1/boards/{KEY}/aggregates?field=&from=&to= returns { field, total, buckets: [{ key, total, count, tickets }] } for one field (id or label; total is the lifetime one); from / to are period keys, inclusive (default the last 30 days / 12 weeks / 12 months). The same as GET /v1/board/aggregates?board=, SDK tm.aggregates() and MCP get_aggregates.

M · The migration

scripts/migrate-aggregates.mjs (logic in scripts/lib/aggregates.mjs, unit- and emulator-tested) turns the cost counters into the aggregate shape. For every board, archived ones too:

  • aggFields ||= [COST_AGG_FIELD]; a list without cost gets it first; a list with cost — archived or not — is left alone.
  • board.aggs.cost and every ticket.aggs.cost = { total: cost.usd, count: cost.runs }.
  • Every stats/{day} → aggStats/daily:{day} fields.cost (other fields in that document are kept).
  • Every message with run and no agg, inline and in data pages, gets agg: { entries: [{ fieldId: 'cost', value: run.costUsd }] }.

The legacy counters are the full truth for cost (the backend still writes them, and seeds aggs.cost from them on a board not yet migrated), so a counter that differs is corrected from them and listed. Values are compared before every write: a re-run writes nothing. Dry run by default; nothing is deleted. 

pnpm --filter @tm/shared build
node scripts/migrate-aggregates.mjs --project <id>           # dry run
node scripts/migrate-aggregates.mjs --project <id> --apply   # write
