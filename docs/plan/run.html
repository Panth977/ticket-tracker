Run

The whole app runs on one machine with no accounts anywhere: the project is demo-taskmanager, and the demo- prefix keeps every Firebase SDK on the local emulators. Every outside service — Resend, Meta WhatsApp, FCM, Typesense, GitHub, Slack — sits behind an adapter with a dev fake, and switches to the real thing only when its environment variables are set.

Run it

pnpm dev

One command, in this order (scripts/dev.mjs):

  1. builds @tm/shared and @tm/backend once — the Functions emulator loads backend/lib;
  2. starts tsc --watch for both, so saving a backend or shared file hot-reloads the functions;
  3. starts the emulators: Auth, Firestore, Realtime Database, Storage, Functions (the api function, every trigger, queue and schedule) and Cloud Tasks, with the Emulator UI;
  4. waits for the api function, then seeds demo data;
  5. starts the SvelteKit dev server, which proxies /api, /v1, /mcp, /oauth, /hooks, /ics, /integrations and /.well-known to the api function — the same paths firebase.json rewrites in production.

Ctrl-C stops all of it. Flags: --no-seed (start empty), --no-web (everything but Vite), --persist (keep emulator data in .emulator-data between runs; seeding is skipped when data was imported).

This project has its own port block, so it runs beside other Firebase projects' emulators on their default ports. The seed goes through the real commands (POST /api/*), so every derived document — members, counts, keys, activity, the search index, inbox rows — is what the app itself would have written. The end-to-end tests make their own people and boards (unique addresses and keys), so they run against a fresh stack or alongside a pnpm dev you are using. What they cover:

  • Browser — sign up → Welcome → first board; invite by email → the invitee opens the link and joins; quick add with @ and ! tokens; dragging a card between two others (and seeing it move in a second browser); a conversation with @ and # suggestions, the mention in the other person's inbox, a pin, "Seen by"; custom fields added in settings, grouped and filtered on, saved as a shared view; relating tickets (#refs in a description, a blocked by link and its inverse, the ⛔ card).
  • HTTP — REST with a personal token (idempotency key, scopes); a signed webhook delivered to a real local receiver through the queue; MCP through dynamic client registration, PKCE and the consent screen, then create_ticket from an MCP client; the intake widget; e-mail replies landing in the thread; email-to-board.

Deploy

Production is the Firebase project behind the prod alias in .firebaserc (<your-project-id> below), every function, task queue and schedule in asia-south1. It deploys with no third-party credentials: e-mail, WhatsApp, Typesense and GitHub stay off until their variables exist (table above).

CommandWhat it does
pnpm deploy:prodchecks frontend/.env.production, builds the SPA with it, packages the functions and simulates Cloud Build on them, then firebase deploy --config firebase.deploy.json --project <your-project-id>: hosting, functions, Firestore rules + indexes, Storage and Database rules
pnpm deploy:prod --only functions,hostingthe same with any --only list; other flags (--force, --debug) pass through to firebase deploy
pnpm deploy:prod --dry-runeverything except the deploy itself
pnpm deploy:functions:buildonly the functions package + its Cloud Build simulation (scripts/deploy-functions.mjs --verify)

How the functions are packaged

backend/package.json depends on "@tm/shared": "workspace:*", which Cloud Build cannot install, so the deploy never uploads backend/. scripts/deploy-functions.mjs writes backend/deploy/ (generated, gitignored):

  • lib/index.js — one esbuild bundle of backend/lib with @tm/shared inlined and every npm package left as an import. The handler modules runtime/autoload.ts would discover by listing directories are imported statically ahead of index.js.
  • package.json — only the packages the bundle imports, pinned to the versions installed here; no workspace or dev dependencies.
  • .env.<your-project-id> — copied from backend/: TM_REGION=asia-south1, APP_URL, API_URL, TM_SECRETS. Non-secret values only.

It also writes firebase.deploy.json: firebase.json with the functions source set to backend/deploy and the hosting rewrites pointed at the api function in asia-south1. --verify runs npm install --omit=dev in backend/deploy and loads the bundle in a clean Node, failing unless it exports exactly the functions backend/lib does. firebase.json stays the emulator config (source backend/, us-central1); a predeploy guard stops a plain firebase deploy with it.

Once per project (console / API)

  • Blaze plan; Firestore (default database) and the default Storage bucket in asia-south1 — Firestore and Storage triggers must share the functions' region; a Realtime Database (default instance; asia-southeast1 is the nearest location) before the database rules deploy.
  • Identity Platform enabled (the beforeSignIn blocking function), with the sign-in providers the app uses; <your-project-id>.web.app is an authorised domain by default.
  • The functions' runtime service account (default compute, <number>-compute@developer.gserviceaccount.com) needs Service Account Token Creator on itself (signed attachment upload/download URLs; IAM Service Account Credentials API enabled), Cloud Tasks Enqueuer and Service Account User (enqueueing the queue* functions), and Cloud Run Viewer (the Admin SDK looks up a queue function's URL).
  • A web app registered in the project; its config goes in frontend/.env.production.

Nothing leaves the machine unless one of the variables above is set. There are no real credentials in this repository, and none are needed to run, seed or test anything on this page.
