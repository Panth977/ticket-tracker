Bucket

A bucket is a bucket of files you keep online: notes in Markdown, screenshots, videos, an APK, a spec, a logo. It is a concept of its own, next to boards and artifacts, with its own people. Inside it is a tree of folders and files that you browse as a tree or as folders, preview, and edit as code. What makes it more than a drive is reuse: a ticket can point at a bucket file instead of carrying its own copy, an artifact's page can read (or write) one, and an agent can work in one over MCP. Files kept in a bucket are managed — edited, moved, replaced, deleted — in one place, and every ticket that points at them sees the current version. Since §J a board takes no files of its own: every file put on a ticket goes into one of the board's buckets. Since §K a bucket can also live in its creator's Google Drive, Drive being the source of truth; since §L a board's tickets can too.

A · What a bucket is

  • A named bucket (buckets/{bucketId}): name, description, an emoji, its people, and the boards and artifacts it has been granted to. Created at the root like a board or an artifact, listed in the sidebar under Bucket, hideable from the sidebar, and bundleable into a workspace (agents.html §AB).
  • A tree of nodes (buckets/{bucketId}/nodes/{nodeId}): a node is a folder or a file, with a parentId (null at the root), a name, and its full path (docs/brand/logo.svg) kept on the node so the tree, the breadcrumb and a lookup by path cost one listener and no joins. Paths are unique inside a bucket; a move or rename of a folder rewrites the path of everything under it in the same batch.
  • The bytes live in Storage by file id: buckets/{bucketId}/{fileId}/{fileName}. A node points at its current fileId. Saving a new version (an edit in code mode, a re-upload, an agent's write) writes a NEW file id and then deletes the old object, so a reader never sees a half-written file and a cached URL can never serve the wrong version.
  • Anything goes in: text, Markdown, code, images, video, audio, PDF, APK, zip. The mime type is taken from the upload (or the extension), and the app decides how to preview it.

B · People

Role May
owner everything, including share, grant to boards and artifacts, rename and delete the bucket. Exactly one, the creator.
editor read, upload, edit, create folders, move, rename and delete files and folders.
viewer browse, preview, download.
  • Sharing is by email, like an artifact: bucketShare with a role, null removes; an address without an account becomes an invite.
  • Agents are not shared on a bucket directly. An agent reaches a bucket through a board it is on (§D). That keeps one place — the board — deciding what an agent may touch.
  • Being on a board gives nothing in a bucket, unless the bucket is granted to that board (§D).

D · Grants: a memory used by a board or an artifact

A grant is stored on the bucket: buckets/{m}.boards[boardId] and buckets/{m}.artifacts[artifactId], each 'read' | 'write'. It is set with bucketGrantSet from the board's or the artifact's settings › Subscriptions (Add → pick the bucket → tick Read / Write → Add; Edit; Remove), and the bucket's settings › Subscribers list every board and artifact that uses it. Setting one needs BOTH sides: the caller owns the bucket, and is an admin of the board (or the owner of the artifact). Ending one is either side's call (access: null): the bucket's owner, an admin of that board, or the owner of that artifact — so a board admin can drop a bucket they do not own from their board, and the bucket's owner can drop a board they are not on. Like an artifact's board access (artifacts.html §K), a grant is a ceiling; what a particular person or agent can then do is bounded by their own role.

Grant Who May
board 'read' every member of the board, people and agents browse the bucket, preview and download its files, attach them to tickets on that board
board 'write' editors and admins of the board (people and agents) also upload, edit, create folders, move and delete — through the API, MCP or the attach picker. Commenters and viewers still only read.
artifact 'read' / 'write' the artifact's page, acting as the viewer read (and write) through BackendDriver.bucket, only as far as the VIEWER themselves can reach the bucket — by a role on it, or through a board grant they are on.

bucketReach() (shared/src/bucket/schema.ts) is the one function that answers "what may this principal do here", from the bucket document, the principal's own role and their roles on the granted boards. Every handler, the file door and the driver broker call it.

E · Bucket files on tickets

  • A reference, not a copy. messagePost, ticketCreate and ticketUpdate take bucketRefs: [{ bucketId, nodeId }]. Each becomes a row in ticket.files with source: 'bucket', bucket: { bucketId, nodeId } and the virtual path buckets/{bucketId}/nodes/{nodeId}. Nothing is uploaded; the ticket's storage does not grow.
  • Attaching needs the grant: the bucket must be granted to the ticket's board (read or write), and the caller must be able to comment there. The picker in the composer lists exactly the buckets granted to the board.
  • Viewing resolves the live node. The file door (/api/files/url, agents.html §I) turns the virtual path into the node's CURRENT Storage object, so an edited file shows its new version on every ticket that points at it. Access: the viewer can read the board AND the bucket is still granted to that board — or the viewer reaches the bucket directly. A node that was deleted, or a grant that was removed, shows "No longer in memory".
  • Deleting a ticket never touches the bucket; deleting a bucket file leaves the reference row (it reads as gone).

F · The app

  • Sidebar › Bucket: one row per bucket (🧠 or its emoji), hideable like boards and artifacts; "All bucket" lists them, archived included. /m is the list, /m/{bucketId} the bucket, /m/{bucketId}?path=docs/a.md a file in it, /m/{bucketId}/settings/{general|people|access} its settings.
  • Two views, toggled in the header and remembered per browser: Tree (an explorer tree on the left, the open file on the right) and Folders (a breadcrumb and the current folder's contents as tiles with thumbnails; a click on a folder goes in, on a file opens it).
  • A file has two modes: Preview — Markdown rendered, images, video, audio, PDF, text with highlighting, and for anything else (an APK, a zip) its facts and a Download button — and Code — the file as text in a code editor, editable by editors, saved with ⌘S or Save (bucketFileWrite; a new version). A binary file in Code mode shows its facts and Replace… instead of bytes.
  • Uploads: drop files or whole folders onto the tree or a folder, or Upload. The browser uploads straight to Storage (progress per file), then bucketFilePut registers each node. Files picked with Upload first ask where they go: one field per file holding its full path, folder and name together (/docs/brand/logo.svg, the open folder filled in); a picked folder gets one field for the folder it becomes. A path where a file is replaces it; one where a folder is is refused.
  • Menus: Rename (F2), Move to…, Copy path, Download and Delete (Del) are on every node's menu, and New file / New folder / Upload in its folder. The same menu opens on a right-click — on a node, or on the empty space for the folder itself. A name field takes a path: / separates folders, created as needed, and a leading / starts from the top — so old/a.md as a rename of docs/a.md moves it to docs/old/a.md. The open file's name is a rename button too.
  • Dragging a node (or files from the desktop) lights up the folder a drop would land in, wherever it shows: its whole subtree in the tree, its tile, its breadcrumb, the folder view. Over a file, that is the file's folder; a folded folder unfolds after a moment; a pill by the pointer says Move … into /path. A folder never lights up for itself or what is inside it, nor for the folder the node is already in.
  • Board settings › Bucket and Artifact settings › Bucket: the buckets I own, each with none / read / write.
  • Workspaces: a workspace bundles buckets too (bucketIds); entering one through it keeps the workspace crumb and switcher.

G · API

Scopes bucket:read and bucket:write (consent group "Bucket"). An account token or an OAuth grant reaches the buckets its person reaches; an agent token reaches only those granted to a board the agent is on. Every node is named by path (or nodeId); writing a path creates its missing parent folders.

Command What
bucketCreate / bucketUpdate / bucketDelete the bucket (delete is queued: Storage, nodes, then the document)
bucketShare a person's role, by email
bucketGrantSet a board's or an artifact's access (§D)
bucketList the buckets I reach (optionally: those granted to one board or artifact)
bucketTree every node under a folder (default: all), for a reader who is not on the bucket itself
bucketFileRead a file's text (≤ 1 MB, else truncated) or a signed URL
bucketFileWrite create or replace a file inline: text or base64, ≤ 10 MB
bucketFilePut register a file the app uploaded to Storage itself
bucketFolderCreate, bucketMove, bucketNodeDelete folders, rename / move, delete (recursive)

MCP: every command above is a tool (the bridge, agents.html §AB's neighbour), plus show_bucket in chat. REST: GET /v1/buckets, GET /v1/buckets/{id}/tree, and the raw bytes at GET|PUT /v1/buckets/{id}/files/{path} for files over the inline limit.

I · Decisions

  • D-M1 · Tree in Firestore, bytes in Storage. One listener draws the whole tree (10k nodes at most, each a few hundred bytes); Storage listing would need a call per folder and cannot hold empty folders or a rename.
  • D-M2 · A new version is a new object. Overwriting in place would let a cached URL serve a mix, and a failed write would corrupt the only copy. The old object is deleted after the node points at the new one.
  • D-M3 · Tickets point at the node, not the version. That is the point of keeping it in memory: fix the screenshot once. A ticket that must freeze a version should upload a copy, as before.
  • D-M4 · Agents through boards only. A third place to put an agent would be a third place to forget to remove it.
  • D-M5 · A board takes no files of its own (§J). Two homes for a ticket's file — the board's prefix and a bucket — meant two sets of rules, two sweepers and two answers to "where is that screenshot". One home: the bucket, where it can be found, moved, reused and cleaned up.

J · Ticket attachments live in a bucket

A file put on a ticket — from the composer, a new ticket's description, the API, the intake widget or an e-mail — is uploaded into a bucket granted write to the board and becomes a NEW file there. The ticket holds a reference exactly like §E: a row with path = buckets/{m}/nodes/{n} and bucket: { bucketId, nodeId }. Rows and objects from before (Storage boards/{b}/tickets/{t}/{a}/{name}) keep working for reading, downloading and deleting; nothing new is written there.

The board's default: board.attachBucket

  • boardAttachBucketSet { boardId, attachBucket: { bucketId, template } | null } — board admin, never an agent; the bucket must exist, not be deleting, and be granted write to the board. Written only by the server (boards are not client-writable).
  • The template is a path with variables: <ticketId> (the key, ENG-42), <time> (UTC, 20261005-211946), <random6>, <filename>, <exe> (the extension; <ext> is the same). Default: tickets/<ticketId>/<time>_<filename> (shared/src/bucket/attach.ts).
  • Kept true: bucketGrantSet clears it (same transaction) when that board's grant is removed or lowered to read; bucketDelete clears it on every granted board.

From the app: bucketUploads

  • The app uploads to buckets/{m}/{fileId}/{name} with metadata { boardId }. storage.rules lets the board's admin, editor or commenter create it when the bucket is granted write to that board and is neither archived nor deleting (≤ 1 GB) — besides the bucket's own owner / editors as before.
  • messagePost / ticketCreate take bucketUploads: [{ bucketId, path, storagePath }] (≤ 20). A <ticketId> left in the path is filled with the ticket's key. attachments (board storage paths) is retired: a non-empty list is a 400.
  • Permission is the board's, not the person's bucket role: the bucket is granted write to the board, not archived, not deleting; the command has already checked the caller may post there. So a commenter with no role on the bucket can add a file to it — but only a NEW one: an existing node is never replaced. A taken path (file or folder) becomes name (2).ext, (3)…; a parent that is a file is a 400. Parents are created as usual.
  • One commit. The new nodes are planned and written inside the command's own transaction (backend/src/bucket/attach.ts planBucketUploads), together with the message or the ticket. ticketCreate knows the key there: it is board.key-nextNumber, read before any write, the very number allocateKey then issues. So a refused or failed post leaves no file in the bucket and no row pointing at nothing. When the command fails after the uploads were checked, the uploaded objects that no node points at are deleted (like a failed bucketFilePut); a retried request whose objects are already nodes reuses them.

Bytes the server holds

  • POST /v1/tickets/{KEY}/files and MCP upload_file write the bytes into the board's attachment bucket (or the request's bucket_id, at path when given) and, in one transaction, the new node and the ticket's upload row (source: 'upload', messageId: null, path = the reference). fileIds on post_message works unchanged. No attachment bucket and no bucket_id: 400 "This board has no attachment bucket — set one in board settings › Bucket".
  • The intake widget and inbound e-mail store their files the same way, with <ticketId> left for ticketCreate / messagePost to fill. A board with no attachment bucket still gets the report or the reply — without its files, and with a line saying so ("2 attachments were not saved: this board has no attachment bucket — board settings › Bucket").
  • Housekeeping sweeps abandoned objects under boards/ only. A bucket file is the bucket's, whether or not its ticket row is ever posted in a message; deleting a message or a ticket never deletes it.

Known gaps: an intake or e-mail retried after it already succeeded (idempotent replay) leaves its fresh copies as objects no node points at; nothing sweeps buckets/ for those yet. A board-scoped token acting as a person reaches no bucket (§G), so it cannot read back a ticket file that lives in one.

K · Buckets in Google Drive

A bucket's storage is chosen when it is created and never changes. Managed (the default, no storage field) is everything §A–§J say: nodes in Firestore, bytes in our object store. Google Drive makes the bucket a folder in its creator's Drive, and Drive is the single source of truth: there is nothing to sync because nothing is copied. Firestore keeps only the bucket document — its people, its grants and the folder it points at (bucket.storage = { kind: 'drive', uid, folderId, folderName, email }). People reach it exactly as any other bucket (§B, §D): the server talks to Drive with the connected person's token, so nobody else needs a Drive share.

K1 · The connection

  • Signing in with Google gives the browser an access token for an hour, never the server. So connecting Drive is its own step (Account › Google Drive, or the bucket form): driveConnect → Google's consent page (access_type=offline, scope drive.file only) → GET /integrations/drive/callback exchanges the code for a refresh token → back where the person started with ?drive=connected.
  • The refresh token is kept in _driveLinks/{uid}, sealed with AES-256-GCM under a key derived from the server's signing key. Rules deny every _ collection; no command returns it. Access tokens live in memory. A refused refresh (revoked at Google) marks the link broken: every Drive bucket of that person answers 409 drive_disconnected until they reconnect.
  • Scope drive.file. The app sees only what it created, or folders the person picked with Google's picker (drivePickerToken hands their own browser a short-lived token for it). Files someone adds to the folder by hand in Drive's own UI stay invisible; renames, moves and deletes of the app's files there are seen. The broader drive scope would see everything but is a restricted scope (Google's security assessment).
  • Configuration: TM_GOOGLE_CLIENT_ID + TM_GOOGLE_CLIENT_SECRET (a Web OAuth client whose redirect URI is {API_URL}/integrations/drive/callback); the picker also needs TM_GOOGLE_API_KEY and TM_GOOGLE_APP_ID (the project number). Without a client the option is shown as not set up. Under the emulators (or TM_DRIVE=fake) every connection is an in-memory fake Drive — the whole round trip still runs, tests included.

K2 · Drive is the truth

  • A node's id is the Drive file id (stable across renames and moves: a ticket's reference follows the file wherever it goes inside the bucket). Its path is the names from the bucket's folder down, computed on every read. file.fileId is Drive's head revision, so expectedFileId guards a save as in D-M2. Who made or changed a file is kept in its private appProperties.
  • Every bucket command — bucketTree, bucketFileRead, bucketFileWrite, bucketFilePut, bucketFolderCreate, bucketMove, bucketNodeDelete — and REST's raw PUT answer from Drive in the same shapes. A delete goes to Drive's trash (restorable there for 30 days). A tree is read one Drive query per level. Nothing is written to Firestore by any of them: the bucket's counters stay as created, and the app counts what Drive showed.
  • Names Drive allows and a path cannot hold (/, control characters, ., ..) are shown with a stand-in (a∕b.txt); two items with one name in a folder are told apart with ' (2)'.
  • Drive has no transactions: each write checks, then acts. Two writers racing for one new path can both win (the reader numbers the second). The managed store remains the one with atomic guarantees.
  • The app reads a Drive bucket's tree with bucketTree (there are no nodes to listen to): on open, after each of its own writes, when the tab comes back, and every 20 seconds while it is in front.

K3 · Bytes

A Drive file's bytes are addressed as drive/{bucketId}/{driveId}/{name}. The object-store port routes that prefix to Drive (stat, read, stream with ranges), so the file door, signedAccess and ticket references work unchanged; there is no URL of ours to sign, so it is always the file door's bytesUrl.

K4 · Uploads: straight to Drive

A Drive bucket never touches our object store: Firebase holds where the data is (the bucket document), Drive holds the data.

  • From the app: bucketDriveUpload opens a resumable upload session in Drive with the owner's token (a new file under a reserved id, its folders made first; or a new version of an existing file, with the expectedFileId guard) and answers the session URL. The browser PUTs the whole body there, with progress; the request carries the app's origin, so Drive answers with CORS. Then bucketFilePut with the answered drive/{bucketId}/{driveId}/{name} only confirms the file is in the bucket. The session URL is a capability for one upload; no Google token reaches the browser.
  • Ticket files (§J, purpose: 'attach' — the bucket granted write to the board, the caller may upload there): the file lands in the bucket's hidden staging folder .tm-incoming (never shown in the tree). The post's bucketUploads names it; the command plans it in its transaction like any other (the ticket row points at the Drive id) and right after the commit moves it to its path, a taken name getting ' (2)'. A refused or failed command trashes the staged file; a move that fails after the commit leaves a row that reads as gone (logged; the file stays staged).
  • Bytes the server holds (REST / MCP upload, intake widget, inbound e-mail) go the same way: straight into the staging folder, then placed by the command.
  • Firestore per operation: the bucket document (and, for a member through a board, that board's) to answer "who may" and "where". The Drive connection is read at most once a minute per server instance. Reading a file streams it from Drive through the file door (access is ours to check; viewers have no Drive token).

K5 · Asking where files live

The new-bucket form asks Managed or Google Drive (a folder picked in Drive, else a path made in the Drive's top level, default TaskManager/{name}). The new-board form asks where its ticket files live — a new managed bucket (the default), a new Drive bucket, or none yet — and makes that bucket, grants it write and sets it as the board's attachment bucket (§J). The new-artifact form asks the same (default none) and grants the new bucket to the artifact (§H).

Not in this phase: changing an existing bucket's storage; deleting a Drive bucket removes the bucket here and leaves its folder in Drive untouched; moving a Drive bucket to an org keeps it in its creator's Drive.

K6 · Moving between storages

A bucket's storage is chosen at create and can be moved later, both ways: managed → a folder in the mover's Google Drive, or Drive → managed — from the bucket's own Settings › Storage tab, and only there. A board's or an artifact's Storage tab is about that board or artifact alone (§L4); which bucket a board attaches ticket files to is set in Settings › Subscriptions (§J).

  • bucketStorageMove { bucketId, to } — owner only, in the app. A move to Drive finds or makes the folder (picked, or a path) in the mover's Drive. It stamps bucket.move { to, target, state: 'running', total, done } and queues the job.
  • While it runs the bucket is read-only (writes answer 409 bucket_moving) and is read from where it was; the tab shows n of total live. The job copies node by node in slices of a few minutes, each queuing the next; every slice is safe to repeat (a copied node is skipped). The last one flips bucket.storage in one write.
  • Ticket links keep working. To Drive: each copied file keeps its old id in the private appProperty tmNodeId, and an old id finds it. To managed: the new Firestore nodes take the Drive ids.
  • The old copy. After a move to Drive the managed objects and node documents are deleted. After a move back to managed the Drive folder is left exactly as it was — nothing in a person's Drive is ever deleted by the app.
  • A failed slice sets state: 'failed' with the error; nothing is lost (the bucket still reads from where it was) and the owner starts the move again.

L · Boards, dictionaries and artifacts in Google Drive

A board can keep its tickets — fields, task lists, messages, activity — in a folder of its creator's Google Drive, not just its files. Drive is the single source of truth; the database keeps only where they are. Notifications, unread marks, agent events, aggregates and the board's own settings stay in the database (they belong to a person or to the board, not to a ticket).

L1 · The files

<board folder>/tickets/<ticketId>/meta.json          the ticket document, minus its messages
<board folder>/tickets/<ticketId>/messages/<ISO time>_<messageId>.json   one file per inline message
<board folder>/tickets/<ticketId>/pages/<NNN>.json    older messages and activity, packed (agents.html §W)

One entity, one storage. A board, a bucket, an artifact and a dictionary each choose their own: managed or a folder of Google Drive, picked on create and moved only from that entity's own Settings › Storage. A board's attachment bucket (§J) is a bucket like any other — it is never inside the board's folder and never moves with the board.

A Drive ticket keeps at most 40 messages inline (20 after a spill) — a cold read downloads each file, so its thread packs into pages sooner than a database ticket's (200/100). Every meta.json carries the private appProperties tmBoard, tmTicket: one Drive search lists a board's tickets. A file edited by hand in Drive is what the next read sees (a file that is not JSON reads as empty, never as an error).

L2 · Behind the database port

Nothing above the database changes. backend/src/db/drive/router.ts wraps the adapter: every path under boards/{b}/tickets/ of a board whose storage.kind is 'drive' goes to Drive; every other call is the adapter's own. Queries on a Drive board run in memory with the SQLite adapter's exact Firestore semantics (a list carries meta.json — no thread); collectionGroup('tickets') merges the database's answer with every Drive board's and orders and limits them as one. A Drive board is not in the search index: its tickets are matched in memory. onTicketWritten runs after each Drive write (board counts), as Firestore would have run it.

L3 · Writes take turns

Drive cannot refuse a stale write, so the database keeps one small document per ticket, boards/{b}/driveRev/{t} { v, at, lease, folderId, messagesId, pagesId, metaId }. A transaction reads Drive freely; before the database commits, it takes the lease of every Drive ticket it changes (in path order) and checks v is still what it read — changed, and the whole transaction runs again. Then the database commits, the files are written, and the lease is given back with v + 1. A lease runs out after a minute if its writer dies.

Live. The browser reads a Drive board's tickets through the ticketDocs command (frontend/src/lib/firebase/routedFirestore.ts answers the app's Firestore reads with it). It listens to the board's driveRev documents: when one moves — the ping after every write — it reads again; and it reads again once a minute regardless, for edits made in Drive by hand.

L4 · Choosing and moving

  • Create pages › Google Drive — a board (boardCreate { storage }, tickets in <folder>/tickets), a dictionary (dictionaryCreate { storage }) or an artifact (artifactCreate { storage }). The folder is picked, or TaskManager/<name> is made. The new-board and new-artifact pages ask a second, separate question for the new file bucket they make (managed, Drive in its own folder, or none) — §K5.
  • Settings › Storage on a board, dictionary and artifact — that entity only, never its buckets: entityStorageMove { kind, id, to | resume } — a board's admin, a dictionary's / artifact's owner, in the app. A queued job (entityStorageMove): settings and subtrees in one step, then tickets one by one; <kind>.move shows progress; everything it keeps is read-only meanwhile (409); resumable. To Drive: the database's copy is deleted after the switch. Back: nothing in Drive is deleted. Buckets move from their own Storage tab (§K6).
  • Archived tickets live in <board folder>/archive/<id>/, the same files; archiving or restoring moves the folder. Each meta.json carries tmState, so a list of active tickets (the board, My work) never downloads an archived one.

L5 · Every entity, not only tickets

The workspace — who owns what, who may see it, names, keys, counters — stays in the database: it is the instance's index, and the security rules read it. What an entity is lives in its Drive folder (backend/src/db/drive/entities.ts):

EntityIn DriveStays in the database
Boardsettings.json (stages, priorities, tags, fields, aggregate fields, default view, settings), views/, templates/, webhooks/ and integrations/ (sealed), tickets/, archive/name, key, people and roles, counters, attach bucket, a webhook's delivery log
Dictionarycontent/entries.enc.json (sealed)name, people, grants
Artifactdb/data/… — its data tabs, one file per documentname, people, read-only flag, builds (served from our CDN), viewers' kv, realtime data
Bucketits files (§K)name, people, grants

The router splits an entity document's write by field: settings go to the file, every other field stays a database write in the same transaction (counters and access stay atomic). A subtree document maps onto folders by its path (db/data/orders/o1 → db/data/orders/o1.json). Every write takes a turn through <kind>/{id}/driveRev/{key} (§L3). The browser reads them through driveDocs, and an artifact's broker writes its data through driveDocWrite (same gates as the rules).

L6 · Secrets

Each Drive entity has a random 256-bit data key; secret subtrees are AES-256-GCM sealed with it ({"$tm":"tm/sealed@1",…}). The key is in .tm-keys.json, wrapped twice: sealed for this instance, and wrapped (X25519 + HKDF + AES-GCM) to the Drive owner's recovery key. The recovery code — its private half — is shown once (Account › Google Drive, driveRecoveryCode); the database keeps only the public half (_driveVaults/{uid}). Lose the code and this instance together and the secrets are gone; everything else is plain JSON.

L7 · Import, and the scope

Every entity folder has .tm-entity.json (kind, original id, name, a board's key, people by e-mail), rewritten after its document changes. Account › Google Drive › Import (driveImport { folderId, recoveryCode? }) makes the folder an entity again with its original id; the importer owns it (a board: admin), the manifest's other people come back as a list to invite. A board's key must be free; its ticket keys and numbering are rebuilt from the files; a files/ folder written by an older version comes along as a bucket. Sealed by another instance → the recovery code re-seals the data key here.

drive.file sees only what this Google app made or the person picked — another TaskManager (another Google app) may not see a folder's children. An instance can ask for the whole Drive instead: TM_DRIVE_SCOPE=drive (a restricted scope: fine for a self-hosted instance in Google's testing mode; a public app needs Google's verification).
