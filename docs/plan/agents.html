Agents

Phase 2 turns TaskManager into the place your own orchestrators work. An orchestrator reads tickets, runs agents, and the agents write back to the tickets: comments, Markdown and HTML documents, status changes. This page is the spec the phase-2 build follows. It covers agents as members of a board, tokens that carry an agent's identity, the REST and MCP API, and a conversation view that opens images, video, audio, Markdown and HTML natively.

A · Principals: people and agents

Anyone who can appear on a ticket is a principal. That is either a person (their Firebase uid) or an agent, whose id is ag_ plus 16 characters. Both are stored in the same fields: board.access keys, members/{id}, assigneeUids, watcherUids, mention nodes, message.authorUid, and activity.actor. An id's prefix tells you what kind it is, and members/{id}.kind is 'user' | 'agent'.

  • Agents never sign in to Firebase. They act only through a token, so they never appear in readerUids, and the Firestore rules never see them.
  • The UI draws every principal with one component. An agent shows its profile picture and an Agent badge wherever a person would appear.
  • Agents are not sent push, email or WhatsApp. They get an event inbox instead.

B · Agent profiles

agents/{agentId}
  ownerUid: Uid                 // the person who made it; only they see or change it
  name: string                  // 1–60
  avatarPath: string | null     // users/{ownerUid}/agents/{agentId}/avatar/{millis}.webp
  icon?: string | null          // a prebuilt icon id (shared AGENT_ICON_IDS: brand marks + generic glyphs); avatarPath > icon > initials
  systemPrompt: string          // Markdown, ≤ 50 000 chars
  description: string | null    // one line, shown in pickers
  createdAt, updatedAt: Millis
  archivedAt: Millis | null     // archived: off every board, its tokens revoked

The Agents page is in the sidebar under You, and each agent's page is /agents/{agentId}. On it you set the name, picture (uploaded and cropped like your own) or a prebuilt icon (a brand mark — Claude, Gemini, ChatGPT, Copilot, Mistral, Llama, Cursor — or a generic glyph, drawn on the agent's colour like initials; a picture wins over an icon), description and system prompt, with a Markdown editor and a preview. The page also lists the boards the agent is on and the tokens that act as it. Commands: agentCreate, agentUpdate, agentArchive. Only the owner can read or write an agent. Its system prompt is given to its token (GET /v1/me, MCP whoami), so an orchestrator can load the prompt from the token alone.

C · Agents on boards

  • A board admin who owns an agent adds it directly, with no invite, in People & roles › Add agent. It gets a role of editor, commenter or viewer (never admin) and an optional StageGrant. Command: boardAgentSet {boardId, agentId, role | null, stageGrant?}. role: null removes the agent.
  • Any board admin can change the role of an agent that is already on the board, or remove it. Only the owner can add it.
  • Removing an agent works like removing a person: it is taken off assignees and watchers, and its messages stay.
  • members/{agentId} = { kind: 'agent', role, stageGrant, name, avatarPath, icon, ownerUid, addedBy, joinedAt }. Renaming the agent or changing its picture or icon is copied out to every board it is on, the same way a person's profile is.

D · Assignment, mentions, and the agent inbox

  • The assignee picker and the @ menu list people and agents on the board. Agents are marked with their badge.
  • Every notify() recipient that is an agent gets a document in agentInbox/{agentId}/events/{eventId}: { type: assigned | unassigned | mentioned | comment | stage | updated | created, boardId, ticketId, ticketKey, messageId?, actor, summary, createdAt, ackedAt }. An agent receives events for tickets it is assigned to or watching, and for any message that mentions it. The agent's own actions never create events for itself.
  • A token reads its agent's events through REST (a cursor feed, an SSE stream, and ack) or through the MCP tools get_events and ack_events. Board webhooks keep working for push-style orchestrators.

E · Tokens: one board each, optionally acting as an agent

Account › Tokens lists every token and has a New token button. The form asks for:

What a token may do is its scopes ∩ what its principal's board role allows (can()). So an agent that is a commenter can never move a ticket outside its StageGrant, whatever the token says. The token string (tm_live_…) is shown once, together with a ready-to-paste MCP config and curl examples. It is stored hashed at users/{uid}/apiKeys/{keyId} as { name, boardId, actsAs: {kind, id}, scopes, prefix, hash, expiresAt, lastUsedAt, revokedAt }. Every change a token makes is attributed "Builder (agent) via token orch-eng-builder". Archiving an agent, or removing it from the board, revokes its tokens for that board.

H · The conversation

  • Messages render GitHub-flavoured Markdown: headings, lists, task lists, tables, block quotes, links, inline images, and code blocks with syntax highlighting and a copy button. Human messages written in the editor render the same way.
  • Long messages (over about 40 lines) collapse behind "Show more". Code blocks over 30 lines scroll.
  • Message actions: reply (quote), react, pin/unpin, edit, delete, copy as Markdown, copy link. Agents' messages carry the badge and "via token …".
  • Composer: drag, drop or paste many files at once, with a progress bar each. Files can be removed before sending, and a message can be sent with files only. Sending uses ⌘↵.
  • Attachments show as preview cards in a grid under the message, and the same cards fill the drawer's Files tab.

K · Feel: motion, loaders, and work that never blocks

No click waits for the server. Every write goes into an outbox. The UI updates at once and stays usable, the command runs in the background, and only a failure asks for attention.

The outbox

  • One client module, lib/api/outbox, used by every write: queue(command, input, { optimistic, rollback, draft, openTo }). It applies the optimistic change right away, sends in the background, and retries up to 3 times with backoff while online. It waits while offline and resumes when the browser comes back online.
  • Entries for messages, and anything else with a draft, are persisted in IndexedDB (falling back to localStorage) for each user, so an unsent message survives a reload or a closed tab and is retried on the next visit.
  • A small Syncing · 2 indicator sits at the bottom of the sidebar while anything is pending. It turns into ⚠ 1 failed, and clicking it lists the failed items with Open and Cancel.

When something fails

A toast stays until you act on it: “Couldn't create Fix login copy · Open · Cancel”.

  • Open goes to where the change was made and puts it back. A ticket reopens the full create form, prefilled from the draft. A settings change reopens that section with the edited values. A message goes to its ticket with the failed bubble highlighted.
  • Cancel drops the change and rolls back what the UI showed.

Creating a ticket

The dialog closes the instant you press Create. The card appears in its column straight away, dimmed, with a small spinner and the key VDP-…, and becomes a normal card with its real key when the server answers. If creation fails, the card shows a red edge and the toast above appears, where Open reopens the prefilled form.

Sending a message, the way chat apps do it

  • The composer clears on send and is never disabled. The bubble appears at once with a status mark: 🕓 sending, ✓ sent, or a red ! for failed. Attachments show their upload progress inside the bubble.
  • Clicking a failed bubble opens a menu with Resend and Cancel (cancel deletes it; Edit is optional).
  • A ticket with unsent messages shows ⚠ on its board card, on the drawer's Thread tab, and in My work.

The thread looks like Google Chat

  • Your messages sit on the right in an accent-coloured bubble, without an avatar. Everyone else's sit on the left in a neutral bubble, with their avatar and name (plus the Agent badge for agents). You see who said what without reading names.
  • Consecutive messages from the same author within 5 minutes are grouped: the name and avatar show once, the bubbles stack tightly, and the time appears on hover, plus under the last bubble of the group. Day separators ("Today", "Yesterday", a date) sit centred between days.
  • System lines ("Priya moved this to QA", "referenced from ENG-40") are small, centred and grey, not bubbles.
  • Markdown, code and attachment cards render inside the bubble; wide content (tables, code, HTML previews) may widen the bubble to the pane's width.

Unread, and marking as read

  • When a ticket opens, the app reads your last-read time for it (users/{uid}/reads/{ticketId}.readAt), then marks the ticket read (readAt = now). The old value is kept for as long as the ticket stays open.
  • In the thread, a divider labelled New messages is drawn before the first message newer than that old value, and the thread opens scrolled to it. Messages arriving while the ticket is open are read at once (the pointer advances when they are in view) but stay below the divider.
  • In Activity, the same kind of divider, labelled New, is drawn above the entries newer than the old value (the list is newest first).
  • Your own messages and changes never count as unread. The unread badges on board cards, My work and the sidebar clear when the ticket is opened.

The ticket view: two panes, no tabs

There are no Thread, Activity or Files tabs. The ticket (the drawer, and the /t/{key} page) is split into two columns, and each column scrolls on its own.

Left, widerRight
Title and description, fixed at the top (the description collapses to a few lines with "Show more" when it is long); under them the thread, which scrolls in its own space; the composer is pinned to the bottom, whether the thread is empty or long, and an empty thread's message is centred above it Metadata fields (stage, priority, assignees, dates, estimate, tags, custom fields, links / related), then the Attachments section (every file on the ticket as preview cards), then the Activity section (the change history, newest first, loading more on scroll); each section can be collapsed, and the column scrolls on its own

L · Seeing what an agent is doing: questions, task lists, heartbeat

L1 · Questions with options

An agent can ask a question that appears in the thread as a form card. A person fills it in and submits it, and the answer comes back to the agent as structured data.

Question (a message with kind: 'question')
  title: string                      "Which database should the report use?"
  body: RichText | null              optional context, Markdown
  fields: QuestionField[]            1–10
    { id, label, type: 'single' | 'multi' | 'text' | 'longText' | 'number' | 'boolean' | 'date',
      options?: { id, label, description? }[],   // single / multi
      required?: boolean, default?, placeholder? }
  allowComment: boolean              adds "Anything else?"
  to: PrincipalId[] | null           who should answer (null = any person on the board)
  blocking: boolean                  true: the ticket shows "Waiting for your answer"
  status: 'open' | 'answered' | 'cancelled' | 'expired'
  expiresAt: Millis | null
  answer: { values: Record<fieldId, value>, comment?, by: Uid, at: Millis } | null
  • In the thread: an open question is a card on the asker's side, with the form inside: radio buttons for single choice, checkboxes for multiple choice, inputs for the rest, and a Submit button. Once answered, the card locks and shows the chosen values with "Answered by Panth · 10:42", and the answer also appears as your reply bubble. A person with commenter rights or above can answer. When to is set, only those people can answer, and the card says whom it is waiting for.
  • Visibility: a blocking open question puts a ❓ Waiting for you badge on the ticket card, the drawer header and My work, and notifies the to people (or the assignees and watchers) through their normal channels as the event question.
  • The agent gets the answer as an inbox event answered carrying the values, and can also read it with GET /v1/questions/{id}. The agent can cancel its question, and an expired one locks as "Expired".
  • Commands: questionAsk, questionAnswer, questionCancel. The outbox handles Submit like any other write.

L2 · Task lists inside the ticket

An agent publishes its plan as a checklist and ticks it off as it works.

tickets/{t}/tasklists/{listId}
  title: string                      "Plan: add CSV export"
  owner: PrincipalId                 usually the agent
  items: { id, title, status: 'todo' | 'doing' | 'done' | 'skipped' | 'failed', note?: string, updatedAt }[]   ≤ 100
  position, createdAt, updatedAt, closedAt: Millis | null
  • Where it shows: at the top of the right pane, above the fields. Each list has a progress bar ("4 / 7"), and the item being worked on (doing) is highlighted with a spinner; failed items are red, with their note. The ticket card shows a compact "4/7" chip.
  • Creating a list and finishing it each add a system line to the thread. Every change to an item does not, to keep the thread readable.
  • The owner (through its token) and editors can change a list. People may also tick items by hand.
  • Commands: tasklistSet (create or replace the whole list), tasklistItemUpdate (one item's status and note), tasklistDelete.

L3 · Heartbeat: is the agent alive?

The orchestrator sends a heartbeat every minute while it works, and a final one when its work ends.

POST /v1/heartbeat   (MCP: heartbeat)
  { ticket?: KEY,                    // omit = an agent-level beat, with no ticket
    state: 'working' | 'idle' | 'done' | 'error',
    message?: string,                // "Running tests (3/12)"  ≤ 200
    progress?: number }              // 0–1, optional

boards/{b}/agentStatus/{agentId}__{ticketId | '_'}
  agentId, ticketId | null, state, message, progress, lastBeatAt, startedAt, endedAt

Heartbeats go to their own small documents rather than the ticket, so a beat every minute doesn't retrigger the ticket's search indexing or re-render every listener. The board listens to agentStatus once, and every card and drawer reads from that. What the UI shows is computed from the state and the time since the last beat:

ConditionShown as
state working, last beat ≤ 75 s ago🟢 a pulsing dot + "Working · Running tests (3/12)" on the ticket header and the agent's avatar; a green dot on the card
state working, last beat > 75 s ago🔴 "No signal for 3 min" in red. The orchestrator may have died. A scheduled sweep notifies the agent's owner after 5 minutes of silence (once per silence).
state idle🟡 "Idle · waiting for an answer" (usually after asking a blocking question)
state done⚪ "Finished · 10:42". Nothing is running on this ticket.
state error🔴 "Stopped with an error" plus the message
no status yetnothing

The Agents page shows each agent's agent-level status and its tickets currently being worked on. People & roles shows the same dot next to each agent. The token needs the scope status:write, which is part of the Worker preset.

M · The SDK your orchestrator imports

Writing a client by hand for every orchestrator is the thing this app exists to avoid. So the app ships a small, typed JavaScript SDK, hosted next to it, that turns every REST call and every MCP tool into a function.

Where it lives

https://taskmanager-example.web.app/lib/               an index page: install lines per runtime, examples
   /lib/v1/sdk.js          ESM bundle, no dependencies   (browsers, Deno, Bun)
   /lib/v1/sdk.d.ts        one flat declaration file
   /lib/v1/sdk.ts          the same SDK as a single TypeScript file (Deno and Bun type it natively)
   /lib/v1/sdk.min.js
   /lib/v1/tm-sdk-<version>.tgz  and  tm-sdk.tgz   npm install for Node
   /lib/v1/openapi.json    a copy of the API description
   /lib/latest/…           the newest build (never cached)

/lib/v1/* is immutable and cached for a year; /lib/latest/* is never cached.

Type hints in every runtime

A URL import only carries types if the server says where they are. All three mechanisms are used, so an editor and a compiler both find them:

RuntimeInstallHow types arrive
Node (npm, pnpm, yarn, bun install) npm i https://taskmanager-example.web.app/lib/v1/tm-sdk.tgz
then import { createClient } from '@tm/sdk'		 The tarball's package.json carries types, exports (with a types condition) and the .d.ts. It is a normal dependency, so tsc and every editor resolve it. Node cannot import over https, so this is the supported path — pin a version with the versioned tarball name.
Deno import { createClient } from 'https://…/lib/v1/sdk.ts'
or map it in deno.json: "imports": { "@tm/sdk": "https://…/lib/v1/sdk.ts" }		 Importing the .ts gives Deno the real source, so types need nothing else. If you import sdk.js instead, hosting sends X-TypeScript-Types: /lib/v1/sdk.d.ts and the file also starts with /// <reference types="./sdk.d.ts" /> — Deno honours either.
Bunthe npm tarball, or the URL import like DenoSame as above; Bun reads the triple-slash reference.
Browser / no build step<script type="module"> from /lib/v1/sdk.js Types are not needed at runtime; editors pick them up from the same .d.ts beside it.

Content types are set deliberately: .ts and .d.ts as application/typescript, .tgz as application/gzip, and Access-Control-Allow-Origin: * on /lib/** so a browser or Deno can fetch them. The package is @tm/sdk, built from sdk/ in this repo, and its types come from the same @tm/shared schemas the server validates with, so a wrong field is a compile error rather than a 400.

What it gives you

import { createClient } from 'https://taskmanager-example.web.app/lib/v1/sdk.js'

const tm = createClient({ token: process.env.TM_TOKEN })   // one board, one identity: the token decides

const me = await tm.me()                    // principal, board, scopes; for an agent its systemPrompt
const mine = await tm.tickets.list({ assignee: 'me', state: 'active' })
const t    = await tm.tickets.get('ENG-42')

await tm.tasklists.set('ENG-42', { title: 'Plan', items: ['Read the spec', 'Write it', 'Test it'] })
await tm.tasklists.item('ENG-42', listId, itemId, { status: 'doing' })

const report = await tm.files.upload('ENG-42', { name: 'report.html', text: html })
await tm.messages.post('ENG-42', { markdown: 'Done — see the report.', attachments: [report.id] })

const answer = await tm.questions.ask('ENG-42', {        // resolves when a person submits the form
  title: 'Which database?', blocking: true,
  fields: [{ id: 'db', label: 'Database', type: 'single', options: ['Postgres', 'SQLite'], required: true }],
}).waitForAnswer({ timeoutMs: 30 * 60_000 })
answer.values.db                                          // typed from the fields you passed

const beat = tm.heartbeat.start({ ticket: 'ENG-42', message: 'Running tests' })  // every 60 s
beat.update({ message: 'Writing the report', progress: 0.8 })
await beat.done()                                          // or beat.error('…') — the UI stops showing "working"

for await (const ev of tm.events.stream({ ack: true })) {  // SSE, reconnects, resumes from its cursor
  if (ev.type === 'assigned') …
}
  • Zero dependencies, one fetch (injectable). Node 20+, Deno, Bun and browsers.
  • Errors are typed: TmError with code ('forbidden', 'rate_limited', …), the HTTP status and the problem+json body. Rate limits and 5xx retry with backoff, and every write carries an idempotency key, so a retry is still one change.
  • Helpers for orchestrators: tm.work(handler, { concurrency }) loops over the event stream, keeps a heartbeat alive while the handler runs, marks it done at the end and error if it throws — a whole orchestrator in one call.

Bring your own MCP server

Rather than handing an agent the whole MCP endpoint, an orchestrator can build the tool list it wants:

import { createClient, mcpTools, registerTools } from '…/lib/v1/sdk.js'
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js'

const tools = mcpTools(tm, {
  only: ['get_ticket', 'post_message', 'set_tasklist', 'update_task_item', 'ask_question', 'heartbeat'],
  exclude: ['delete_tasklist'],
  rename: { post_message: 'reply' },
  describe: { reply: 'Reply to the ticket you are working on. Markdown.' },
  defaults: { ticket: 'ENG-42' },        // fixed arguments the model never has to pass (and cannot change)
  wrap: { reply: (call) => async (args) => call({ ...args, markdown: prefix + args.markdown }) },
})

registerTools(new McpServer({ name: 'my-orch', version: '1' }), tools)
  • mcpTools() returns plain definitions — { name, description, inputSchema (JSON Schema), handler } — so they work with any MCP server implementation, not just the official SDK. registerTools() is a convenience for that one.
  • The token's own scopes still apply on the server: a tool you expose that the token may not call fails there. mcpTools drops tools the token's scopes already forbid, so a model is never offered something that must fail.

What gets built

  1. p4-sdk: the sdk/ package — client, helpers, MCP tool factory, flat .d.ts, bundles, tarball, unit tests against a mocked fetch and emulator tests against the real API
  2. p4-hosting: the build and deploy plumbing (artifacts into hosting under /lib/** with the right cache headers), the /lib/ index page with examples, and a Plan › SDK docs page
  3. p4-integration: an orchestrator script written with the SDK, run end to end against the emulators (events → task list → question → files → heartbeat), a type-check of a sample consumer project, then a deploy

N · The same tools, for people

Questions and task lists are not agent features — an agent was simply the first thing that could use them. Everything an agent can do through the API, a person can do in the app. The one exception is the heartbeat (§L3): it is a signal from a running process, so it stays agent-only and read-only in the UI.

N1 · Asking a question from the composer

  • The composer gets an Ask a question action (in the toolbar and as /ask), open to anyone who may comment.
  • It opens a small builder: a title, optional context in Markdown, and fields. Add a field, pick its type (single choice, multiple choice, text, long text, number, yes/no, date), name it, and for the choice types add options — each option a line, reorderable, removable. Mark fields required. Up to 10.
  • Below that: who should answer (anyone on the board, or pick people and agents), blocking (shows ❓ Waiting on the ticket), and expires (never, 1 hour, 1 day, 1 week).
  • A live preview shows the card as the thread will render it. Ask posts it through the outbox like any message.
  • Starting points, so nobody builds a form from nothing: Yes / No, Pick one, Pick several, Free text.
  • The asker (and board admins) can cancel an open question; anyone who may comment can answer, unless the question names people. A person's question notifies exactly like an agent's.

N2 · Task lists people can write

  • The Task lists section in the right pane gets + New list: a title and the items. Paste several lines and each becomes an item — the fastest way to turn a plan into a checklist.

The heartbeat and the agent health dot (§L3). A person is not a process; there is nothing to signal. The UI keeps showing agent health where an agent is involved.

R · An account token, and TaskManager inside Claude

R1 · "Virtual me": a token for the whole account

Board tokens (§E) stay as they are. A third kind is added: an account token, which acts as you across every board you are on — the app without the app.

KindActs asReaches
Board · meyouone board
Board · agentan agent of yoursone board
Accountyouevery board you are on, as it stands at each call — lose access to a board and the token loses it too
  • Scopes still apply. The same checkboxes, applied to every board, plus account-level ones: boards:create, boards:admin (settings and people on boards where you are an admin), agents:write (create and edit your agent profiles), invites:write. Preset: Full account.
  • What an account token can never do, whatever its scopes: create or revoke tokens, grant or revoke OAuth access, change your sign-in or security settings, delete or export your account. A token can never mint another token, so a leak cannot become permanent.
  • Creating one is deliberate: a distinct "Account token" choice, a plain warning of what it can reach, an expiry that defaults to 90 days (never is possible, and says so in red), and the token shown once. The Tokens list marks account tokens clearly and shows last use; revoking is one click.
  • Everything it does is attributed to you, with "via token <name>", exactly like a board token.

R2 · The API and MCP stop assuming one board

  • REST already has /v1/boards; with an account token every board-scoped path takes the board in the path or the key (/v1/boards/{KEY}/tickets, /v1/tickets/ENG-42 — a key already names its board). /v1/me reports kind: 'account' and lists the boards reachable right now.
  • MCP tools gain an optional board argument, required only when the token is account-wide and the call does not name a ticket key. list_boards becomes the natural first call. Board tokens behave exactly as before.
  • The SDK: createClient({ token }) detects the kind. An account client exposes tm.boards.list() and tm.board('ENG') returning the same board-scoped API you already know, so existing code keeps working.

S · Installable: TaskManager as a phone app

The app should install on a phone from the browser and behave like an app once it does — its own icon, no browser chrome, and a window that opens where you left off. It is a progressive web app; there is no store, no native build.

  • Manifest: name "TaskManager", short name "Tasks", display: standalone, portrait-primary, the app's own background and theme colours (matching light and dark), start_url: "/" with a source=pwa marker so installs are distinguishable, and id set so an update never installs twice.
  • Icons generated from one source mark: 192, 256, 384 and 512 px PNGs, a maskable 512 with safe padding (Android shapes), an Apple touch icon (180), and the existing SVG favicon. No stretched screenshots-as-icons.
  • iOS: apple-mobile-web-app-capable, status-bar style matching the theme, the touch icon, and a viewport with viewport-fit=cover. Every fixed bar already respects the safe-area insets; the install path (Share › Add to Home Screen) is explained in-app, since iOS gives no prompt.
  • Install prompt: catch beforeinstallprompt and offer Install once, in the account menu — never a banner over the board. Dismissing it is remembered; it never asks again on that device.
  • One service worker. There are two today: SvelteKit's and Firebase Messaging's. Two workers at one scope fight over the registration, so they merge into one — the app's worker imports the messaging one — and push keeps working exactly as it does now.
  • Offline: the shell (HTML, JS, CSS, icons, fonts) is precached and served cache-first with a versioned cache that is cleaned on activate. Data stays live-only: Firestore's own cache already makes the last board readable offline, and writes already queue in the outbox (§K). An offline page appears only when there is no cached shell at all. A new version shows the existing "update" toast rather than silently swapping under you.
  • Shortcuts in the manifest: Inbox, My work, New ticket — long-press the icon on Android.
  • Proven, not assumed: a Lighthouse installability check in CI (or a scripted check of the manifest, icons, worker scope and offline response) so "installable" is a test, not a claim.

T · Local first: a refresh that shows the app, not a skeleton

Today a reload waits: the root layout holds a skeleton until Firebase Auth restores the session from IndexedDB, and every store starts at loading: true. Firestore's persistent cache already holds the data — the app just refuses to draw it until a round trip it does not need has finished. The rule from here: the last known state paints first, the server patches it.

  • The session is remembered. The last signed-in principal (uid, display name, photo, theme) is written to localStorage on every change and read synchronously at boot, so the shell, the sidebar and the theme render on the first frame. Auth still restores in the background; if it comes back signed OUT, the remembered state is dropped and the guard redirects exactly as it does now. Nothing sensitive is stored — no tokens, no API keys.
  • Stores start from the cache. A live store's first emission must be the cached snapshot when one exists (fromCache: true), never a loading state. loading means "nothing to show yet", not "no server answer yet": once cached data exists the UI is live, and the server's snapshot patches it in place.
  • Stale, and honest about it. Cached-only data renders normally; the top progress bar (§K) is the single signal that a refresh is in flight. No spinner over content already on screen, and no layout shift when the server snapshot lands.
  • What is remembered between visits: the boards list, the last opened board with its views and stages, the ticket last opened, and the inbox count. Firestore's IndexedDB cache does the heavy lifting; what the app adds is the pointer to which of those to subscribe to before the server answers.
  • Bounded. The remembered pointer is per account (keyed by uid) and cleared on sign-out together with the Firestore cache, so a shared device never shows the previous person's boards.
  • Proven: a test that boots the app twice with the network cut — the second boot renders the board — and a recorded first-contentful-paint measurement on reload.

U · The app on a phone

§S made TaskManager installable; this makes it usable once installed. Every screen is checked at 320–430 px through /qa/mobile.html, a QA harness that runs the live app inside phone-sized iframes on the app's own origin (so the frames are signed in), rather than by resizing the browser.

  • The ticket drawer becomes the screen. Below the two-pane breakpoint the drawer is full width; the two panes stack into one scroller and the reply box stays pinned above the safe area. A drawer wider than the viewport — content clipped off the right edge — is the bug this section exists to kill.
  • One thing at a time. Board columns scroll horizontally, one stage per screen; the board toolbar collapses to search plus an overflow rather than two rows of controls at 360 px.
  • Nothing is unreachable. No horizontal page scroll anywhere, no control under the safe-area inset, and every tap target at least 40 px. Dialogs, pickers and menus fit the viewport and scroll inside themselves.
  • Proven: a phone-width e2e pass over the main routes at 390×844 asserting no horizontal overflow and no element wider than the viewport.

V · A notification is a pointer, not a chore

Six unread notifications for conversations I had just read: opening a ticket moved my read pointer (the card stopped looking unread) but the inbox rows that told me about it stayed bold, so the bell kept counting things I had already seen.

  • Opening a ticket reads its notifications. While a ticket is open, every unread inbox row that points at THAT ticket is marked read — including rows that arrive while it is open, because I am watching the thread they are about.
  • Nothing else is touched. Rows for other tickets stay unread, and an invitation is an action rather than a pointer, so it waits for an answer however many tickets I open.
  • It costs nothing extra. The rows come from the bell's own shared inboxUnread listener, and the write shows up locally at once (Firestore latency compensation), so the count drops as the drawer opens rather than after a round trip.
  • Proven: two mentions on two tickets, one of them opened — that ticket's row is read, the other is still waiting, and the bell reads "1 unread".

W · What it costs, and the shape that makes it nearly free

Measured, 23–26 Sep 2026 (₹38.95 over two days; Cloud Functions ₹33.42, Firestore ₹5.17, and 95k Firestore reads on the 25th against 1.9k writes — a 50:1 read-to-write ratio on an app nobody but one person and two agents was using).

WhereMeasuredWhy
api function11,963 billable vCPU‑s of 13,775 (87%), 41,515 requests in 3 days Cloud Run bills CPU for the WHOLE request, waiting on I/O included. Each call costs ~250 ms: an apiKeys collection-group query + board + agent reads, then two cross-region RTDB rate-limit transactions, then the actual work.

The target: 50 boards × 10 live tickets, always on, for ≤ ₹50/month. That means the steady state has to sit INSIDE the free daily quota (50k reads, 20k writes) and keep functions off the read path entirely. The shape that gets there:

  1. One document per ticket. boards/{b}/tickets/{t} carries the fields, the rollup signals (message count, last message, open question, task-list progress, file count, blocked), the task lists themselves, the recent messages, the recent activity and the file list. A board open is ONE query returning ten documents; opening a ticket costs NOTHING extra, because the card already read it. Overflow spills forward into boards/{b}/tickets/{t}/data/{NNN} — 000, 001, … — each page a chunk of older messages, fetched only when someone scrolls back; the ticket doc holds the page count and the oldest inline timestamp. The 1 MB limit is generous: a page is cut at ~700 KB so a write always fits.
  2. Unread with no query. The card compares signals.lastMessageAt with my read pointer, and counts the inline recent messages newer than it. The per-card unread listener — the single worst read amplifier — disappears.
  3. Liveness lives in the Realtime Database, which bills bandwidth, not operations: agent heartbeat, who is viewing, who is typing, and a per-board rev counter the command layer bumps on every write. A heartbeat becomes ~100 bytes instead of a Firestore transaction plus a read in every open tab, and "stopped reporting" is computed from at where it is read, so agentSilenceSweep stops running every minute.
  4. Agents wake, they do not poll. The SDK holds one streaming connection to the RTDB rev/wake path (the RTDB REST stream is plain SSE — no Firebase SDK needed in Deno) and only calls REST when something actually changed, with updated_since / cursor so the answer is the delta, not the world. An idle orchestrator costs nothing. Polling stays supported, but the SDK's own loop backs off to a minute when idle.
  5. The client reads deltas, not screens. Every board query is updatedAt > lastSynced against the persistent cache, so a refresh pays for what changed, not for what is on screen. Firestore charges per document RETURNED: an unchanged board costs one read.
  6. The function gets cheap per call: the resolved API key is cached in the instance for a minute (revocation takes up to that long, which is the trade), the rate limiter counts in memory and only reconciles with the RTDB occasionally, and cpu: 0.5 halves the vCPU-second rate for work that is nearly all I/O wait.

The budget it buys, at 50 boards × 10 live tickets: ~2k writes/day (free), ~5k reads/day (free), RTDB traffic in the low megabytes (free), and functions only on writes — a few hundred vCPU-seconds a day. Call it ₹10–20/month, with the free quota absorbing the rest.

X · Whose app this is: the allow list, and what it costs

TaskManager is private. Sign-up is open in the sense that anyone can sign in with Google — but only accounts on the allow list can DO anything. the configured address (TM_ADMIN_EMAIL) is the admin and is on the list by definition; the admin adds and removes everyone else from a Users module in the account area, beside Agents.

  • Allowed or not, nothing in between. An account that is not allowed signs in, lands on a plain "ask the owner for access" screen, and can reach nothing else: no boards, no tickets, no API, no MCP. The rules enforce it, not the UI — an allowed list in _config/allow (server-owned, like the signing secrets) and a mirrored flag on users/{uid}.allowed so the rules can read it in one hop.
  • The admin is the owner, not a role. One admin address, set in configuration, never editable from inside the app. The Users module lists who is allowed, when they were added and when they last signed in, and lets the admin add an address (before that person has ever signed in) or take access away. Taking access away ends their sessions' usefulness on the next request.
  • No rate limits. The only callers are the owner, the handful of accounts they allow, and their own agents. A limiter here protects nothing and has already stopped an orchestrator mid-run, so it is off (TM_RATE_LIMITS=1 brings it back if this ever stops being private). Costs are controlled by the shape of the app (§W), not by refusing its owner's own traffic.
  • What it costs, in the app. The Users module also answers "what am I spending?" without opening the Firebase console: this month's Firestore reads / writes / deletes, function invocations and vCPU-seconds, RTDB bandwidth, storage and hosting egress — each against its free daily quota — with an estimated bill from a price table kept beside the code. The numbers come from the Cloud Monitoring API (the functions' own service account, roles/monitoring.viewer), cached for an hour, so looking costs almost nothing. It is an ESTIMATE and says so; the console remains the invoice.
  • A budget line worth seeing: today's reads and writes against the free daily quota (50k / 20k), because that is the number that decides whether this month costs ₹0 or ₹600.

Y · What a turn costs: the price on the ticket, the ticket, the board and the day

Measured on the OCZ board, 24–26 Sep 2026: one ticket (OCZ-5) reached $402 over nine runs, and nothing in the app said so. The orch already reads total_cost_usd off every claude -p result line and only writes it to a local log. Money spent on a ticket is a fact about the ticket, so it goes where the ticket's other facts go: the thread, the card, the board, and a chart.

Y1 · A turn is a message with a receipt

  • One run of the agent is one turn. The orch starts claude -p once per turn (fresh, rework, an answer, a comment, a carry-on) and the process exits with one result line. When it exits, the orch posts one message on the ticket — the turn receipt — carrying a run field beside the Markdown: 
    run: {
  n: 3,                       // the orch's run counter on this ticket
  outcome: 'review' | 'waiting' | 'blocked' | 'failed' | 'stopped' | 'timeout',
  costUsd: 1.24,              // THIS turn
  sessionUsd: 21.10,          // the session's running total, as Claude reports it
  durationMs: 743000, apiTurns: 46, model: 'claude-fable-5-1',
  usage: { input, output, cacheRead, cacheWrite } | null
}
    The body is the same thing in words — Turn 3 · review · $1.24 · 12 min — so REST clients, e-mail digests and search see it without knowing the field.
  • Per turn, not per session. Claude Code reports total_cost_usd cumulatively across a resumed session (OCZ-5 run 8: one API turn, zero output tokens, the same $392.83 as run 7). The orch keeps the last reported session total in its state and posts the difference. A run that dies without a result line has no receipt; its money shows up in the next turn's difference, which is honest — it was spent on this ticket.
  • Only the orch posts receipts. The run field is accepted on POST /v1/tickets/{KEY}/messages (and the MCP post_message, the SDK's tm.messages.post) from any token with comments:write; the app's composer never sends it. The thread renders a message with run as a compact receipt row, not a bubble.

Y2 · The sums live where the card reads

  • The ticket carries cost: { usd, runs }, a counter incremented by messagePost in the same write as the message. It is NOT part of signals: signals are recomputed from the document, and the receipts that spilled into data pages are not in the document any more. The drawer header shows it ($402.27 · 9 turns); the card shows it beside the other signals once it is non-zero.
  • The board carries cost: { usd, runs } for its lifetime, incremented in the same transaction. The board bar shows the total; the Boards home tile shows it under the counts.
  • The day is boards/{b}/stats/{yyyy-mm-dd}: { day, costUsd, runs, tickets: { [ticketKey]: { usd, runs } }, updatedAt }, also written in that transaction. The day is cut in Asia/Kolkata (one owner, one clock; a constant in @tm/shared, not a setting), so "today" on the chart is the owner's today. Readable by anyone who can read the board; written only by the command layer.
  • Nothing is scanned. Three counters and one day row per write; the chart reads at most 90 small documents. No collection-group query, no trigger, nothing that §W would have to pay for.

Y3 · Analytics: one board, day by day

  • A section of board settings (/b/KEY/settings/analytics), reachable from the board bar's cost chip. It was first a sidebar child under the open board, and that row appearing and moving as the selection changed read as the list re-sorting itself — the sidebar stays a flat list of boards. It is a page a phone can use: stat tiles across the top (total, this month, last 7 days, today, per finished ticket), then a bar chart of cost per day for the range (30 / 90 days, default 30), then the tickets of the range ranked by spend with their turn counts — each row opens the ticket.
  • Drawn, not imported. The chart is inline SVG in the house style (the usage panel's sparkline already is); a chart library would be the app's biggest dependency for one picture. Bars are the day's cost, the hover/tap shows the day and its tickets, an empty day is an empty slot, and the y-axis picks its own round steps.
  • It reads Firestore directly (the day rows, live), like every other screen: a receipt landing on a ticket moves the bar while the page is open.

Z · Workspaces: every orch in one place, driven from a board

Two repositories carry a hand-written copy of the same orchestrator (bOctupuz/orch and web-03/orch), already diverging: one learnt to survive the daily request budget, the other to carry on after a run ends short. A third project would mean a third copy. The orchestrator is one program; what differs between projects is configuration — the repo, the board, the token, how many agents, which permission mode, the rules that bite in that tree. So the program lives once, in this repository, and each project is a folder of configuration next to it. The folder is what a board can edit.

  • The orch is the same program on every board. It merges the two forks: the request budget and the queued-answer heartbeat from bOctupuz, the bounded carry-on after a short run from web-03, the turn receipt of §Y, and one new thing — it wakes instead of polling. It opens the Realtime Database stream that GET /v1/live hands out (plain SSE, no Firebase SDK) and reads the board only when the board's rev moved, with a ten-minute safety poll. §W measured the old 30-second poll at 88% of all requests; this is the fix at the source.
  • State is per workspace, in the workspace folder, never in the project's tree — a project repo no longer carries an orch/ directory at all. The agents still run with the project as their working directory, so their Claude sessions, memory and CLAUDE.md are the project's.
  • The supervisor is the thing that runs. ws up starts it detached; it starts one orch per enabled workspace, restarts a crashed one with a backoff, and watches the workspace files: a change to a workspace.json, .env or brief.md restarts that workspace's orch (SIGTERM, so a running agent is resumed by the new process, exactly as orchctl restart did); a change under lib/ restarts them all; a new folder with a valid workspace.json is started; enabled: false stops one. ws install writes a launchd agent so it survives a reboot.

Z2 · The ORCH board is a workspace whose repo is the workspaces folder

  • No second program. The board ORCH is handled by the same runtime, configured with repo: workspaces/. A ticket there ("give bOctupuz two agents", "add a workspace for the bindery repo", "the web-03 brief should forbid starting que") becomes a Claude session working in the workspaces folder, whose brief explains the layout, the CLI and the rule that the supervisor applies every file it changes. It edits configuration; it never starts processes. The supervisor notices and restarts what changed; the agent reports what it changed on the ticket.
  • Creating a workspace is ws new. With the account token in workspaces/.env it creates the agent profile (POST /v1/agents), the board from the kanban template (POST /v1/boards — it has the To do / In progress / Review / Done stages the runtime needs), puts the agent on the board as an editor (POST /v1/boards/{KEY}/agents), and writes the folder with a skeleton brief. Those three endpoints are new and account-token only: they are the REST face of agentCreate, boardCreate and boardAgentSet, which the app door already exposes to a signed-in person.
  • The token is the one step that stays with a person — a token can never mint a token (§R1), and that rule is worth more than the convenience. The ORCH agent ends a "new workspace" ticket with a blocking question: mint a Worker token for agent X on board Y (Account › Tokens) and paste it here. The answer resumes the session, which writes it to the workspace's .env; the supervisor starts the orch. The token passes through the tracker once, on a private board; anyone who would rather not can write the line by hand and answer "done".
  • What the phone can now do: open a ticket on any project board and watch an agent work it, ask for a change to how agents work on that project, or ask for a new project — from the same app, with the same drawer. The editor on the laptop is for reading what the agents did, and even that is on the ticket.

Z3 · Migration and decisions

  • bOctupuz and web-03 move first. Each gets a workspace folder with its token, its brief section, its state.json (the session ids survive, so tickets in Review keep their conversations) and its settings; the old orch is stopped, the new one started; the orch/ directory in each repo is left in place until the workspace has run a ticket, then deleted.
  • Decision D-Z1: one supervisor process, orchs as children. Children, not threads, so a crash in one board's orch never takes another's down, and so a restart on a config change is a process boundary, not a hot-reload puzzle.
  • Decision D-Z2: the runtime keeps zero dependencies (the reasoning in the web-03 README stands: a thing whose only job is to still be running at three in the morning has no install step).
  • Decision D-Z3: no worktree per ticket yet. Agents on one board share the project's checkout as before; the brief carries the discipline. A worktree per ticket is a workspace option to add when a board needs it, not a default.
  • Decision D-Y1: the cost day is cut in the owner's timezone by a constant, not a board setting. There is one owner.
