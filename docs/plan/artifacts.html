Artifacts

An artifact is a small website that lives inside TaskManager: a dashboard, a tracker, a form, a tool. Somebody (usually an agent) writes the frontend in whatever they like, builds it to a static folder, and publishes that folder. TaskManager keeps it in Firebase Storage and shows it only to the signed-in people it has been shared with. The artifact's backend is a script tag: window.BackendDriver gives it Firestore, the Realtime Database and Storage, all fenced inside a prefix that belongs to that one artifact. Artifacts are a concept of their own, separate from boards: no tickets, no stages, their own people.

A · What an artifact is

  • A static build, nothing else runs on our side. The published thing is a folder with an index.html at its root: plain HTML/CSS/JS, or the dist/ of Svelte, React, Vue or anything else. We never build it and never run it on the server. The only rules for the build: relative asset paths (Vite base: './'), and hash routing or a single page (a deep link that is not a file falls back to index.html, so history routing mostly works too).
  • Its data is its own. Everything an artifact stores goes under its prefix: artifacts/{id}/db/data/… in Firestore, /artifactData/{id}/… in the Realtime Database, artifacts/{id}/files/… in Storage. The artifact's code never learns these prefixes and cannot write outside them.
  • Its people are its own. An artifact has an owner and a list of people (and agents) it is shared with, each with one role. Being on a board gives you nothing on an artifact, and the reverse.
  • Builds are versions. Every publish is a new build. The artifact points at a current build; the last ten are kept and any of them can be made current again (a rollback is one click). Publishing never touches the data.
  • The source can travel with it. A publish may carry a zip of the source beside the build. It is never served; it is what the next agent downloads to carry on where the last one stopped.

B · Who can see and change one

vieweryesyesyes, unless the artifact is set read-only for viewersnono
  • Only signed-in, allowed accounts, and only the ones it is shared with. Nothing about an artifact (its files, its data, its name) is reachable without a session whose uid is in artifacts/{id}.access. There is no public link and no "anyone with the link". An account not on the allow list (§X in Agents) can never be given a role.
  • Viewers write by default, because most of what gets built this way (a poll, a checklist, a log) is useless read-only. One switch in the artifact's settings makes viewers read-only.
  • Sharing works like board invites. The owner adds an email with a role. If that person already has an account they get the role at once and a notification; if not, an invite waits for their first sign-in (same invites/ flow, with artifactId in place of boardId).
  • Agents are members too. An agent (one of yours) can be added as an editor. Its token then reaches that artifact and only that one (C4).
  • Taking access away is immediate for data: the rules read the access map on every call. The static files it had already loaded stay loaded until the tab closes, and a file link it held stops working within the hour (D2).

C · How the code gets there: publishing

C1 · The one call

POST /v1/artifacts                         create      { name, description? } → { id, url }
POST /v1/artifacts/{id}/builds             publish     body: a zip of the build folder (application/zip)
                                                        ?source=1 + multipart part "source": a zip of the source (optional)
                                                        ?message=… a line saying what changed
GET  /v1/artifacts                         list the ones you can reach
GET  /v1/artifacts/{id}                    meta + current build + builds[]
POST /v1/artifacts/{id}/builds/{b}/current roll back (or forward) to a build
GET  /v1/artifacts/{id}/source             the newest source zip (a short-lived URL)
PUT  /v1/artifacts/{id}/access             { email, role } share / change role;  role: null removes
DELETE /v1/artifacts/{id}                  owner only; deletes files, builds and ALL data
  • The server unpacks and checks the zip: an index.html at the root (or in a single top folder, which is stripped), at most 25 MB unpacked and 2,000 files, no path escaping the folder, no symlinks. Each file goes to artifacts/{id}/builds/{buildId}/… in Storage with its content type. The build is written as artifacts/{id}/builds/{buildId} (files, bytes, message, who, when) and becomes current in the same command.
  • A check that catches the usual mistake: if index.html references /assets/… (an absolute path, Vite's default) the publish still succeeds but answers with a warning naming the fix (base: './'), because such a build shows a blank page.

C2 · The same thing from the SDK, MCP and the Claude plugin

// SDK (Node / Deno): zips the folder for you

await tm.artifacts.publish(art.id, './dist', { source: './', message: 'first cut' });

// MCP tools
artifact_list · artifact_get · artifact_create · artifact_publish · artifact_rollback · artifact_share · artifact_source
  • artifact_publish over MCP takes files, not a zip: [{ path, content, encoding: 'utf8'|'base64' }], up to 5 MB in one call. That covers a hand-written HTML/CSS/JS artifact straight from a chat. A framework build goes through the SDK or REST, from the machine that built it.
  • The Claude plugin gains a skill, artifact: how to scaffold one (a Vite template with base: './' and the driver tag already in index.html), how to run it locally against the mock driver (E5), and how to publish. llms-full.txt gets an Artifacts chapter generated from the same sources, so an LLM handed that one file can build one.

C3 · From the app

  • An owner or editor can also drop a zip (or a folder) on the artifact's Builds tab. Same command, same checks.

C4 · Tokens

  • Two new scopes: artifacts:read (list, get, download source) and artifacts:write (create, publish, roll back, share). An account token reaches every artifact where you are owner or editor; creating one needs artifacts:write. An agent's token reaches only the artifacts that agent is a member of. It may create one: the artifact then belongs to the agent's owner (it appears in their sidebar at once, with an inbox row) and the agent is on it as editor, so it can publish but never share, rename or delete. Nothing here lets a token mint a token, as everywhere else.

D · How it is served: two origins and a sandbox

This is the part that has to be right. An artifact is code written by somebody else, often by an agent, and it runs in the browser of everyone it is shared with. If it ran on taskmanager-example.web.app it could read the viewer's Firebase session out of IndexedDB and do anything that person can do: read every board, post as them. So artifact code never runs on the app's origin and never holds a Firebase session.

D1 · The shape

taskmanager-example.web.app/x/{id}          THE HOST PAGE: our Svelte code, the viewer's real session
  └─ <iframe sandbox="allow-scripts allow-forms allow-popups allow-downloads allow-modals"
             src="https://taskmanager-example-usercontent.web.app/c/{capability}/index.html">
        THE ARTIFACT: its own files, an opaque origin, no cookies, no storage, no session
        window.BackendDriver  ──postMessage──▶  host page  ──Firebase SDK, as the viewer──▶  artifacts/{id}/… only
  • A second Hosting site, taskmanager-example-usercontent, in the same project. Its only route, /c/**, rewrites to the api function, which streams the file from Storage. Nothing of the app is served there: no index.html, no service worker, no /api.
  • The sandbox, twice. The iframe has sandbox without allow-same-origin, and every response from the usercontent site carries Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups allow-downloads allow-modals. The header covers the case where somebody opens the file URL as a top-level page: it still gets an opaque origin. Either one alone would do; both is cheap.
  • What the opaque origin costs the artifact: localStorage, sessionStorage, IndexedDB and cookies throw or do nothing. The driver's KV (E2) replaces them, and it syncs across devices, which they never did. fetch to public APIs and CDNs works (the origin is null; most public CDNs allow it).

D2 · The capability in the URL

  • The iframe cannot send a session, so the file URL carries one. When the host page opens an artifact it calls artifactOpen(id); the command checks the caller's role and answers { capability, build, role, readOnly }. The capability is an HMAC-signed string of { artifactId, buildId, uid, exp }, valid for one hour, signed with a key kept beside the other server secrets.
  • It is a path segment, so the build's relative URLs (./assets/app.js) carry it automatically. /c/{cap}/{path} verifies it, maps path to artifacts/{id}/builds/{buildId}/{path} (a missing path without an extension → index.html) and streams it with its content type, Cache-Control: private, max-age=3600, immutable (a build never changes) and the CSP header.
  • The host page asks for a fresh capability before the old one expires, so a tab left open all day keeps loading lazy chunks. It carries a build id, so publishing a new build does not break a tab that is open on the old one; the host shows a "new version, reload" bar instead.

D3 · The host page

  • /x/{id} in the app: a thin top bar (name, build, Share, Settings, full-screen) and the iframe filling the rest. Full-screen hides the bar, so a dashboard can live on a wall screen. On a phone it is the same page under the ☰ drawer.
  • The host is the broker (E3). It holds the viewer's Firebase session and the artifact's id, listens for messages only from its own iframe (event.source === iframe.contentWindow), and turns each request into a call on a path it builds itself. The iframe never sends a full path, only the part after the prefix.

E · The driver: window.BackendDriver

E1 · Loading it

<script src="https://taskmanager-example.web.app/backend-driver/v1/driver.js"></script>
<script>
  const db = window.BackendDriver;
  await db.ready;                                    // handshake with the host done
  const me = db.me;                                  // { uid, name, email, photoURL, role, readOnly }
  const doc = await db.firestore.get('/my/doc');     // → artifacts/{id}/db/data/my/doc
</script>
  • Served from /backend-driver/** on the app site with the same headers as /lib/** (CORS open, nosniff, a pinned v1 cached for a year and a latest that is not). Also as an ES module (driver.mjs) and on npm-by-URL with its .d.ts, like the SDK, so a Vite or TypeScript project gets types.
  • It has no Firebase in it. It is a few kilobytes of postMessage plumbing, a Promise per request and a callback per subscription. All the Firebase code, and the session, stays in the host page.
  • The artifact id comes from the host, in the handshake, not from the URL the artifact can see. The artifact can read it (db.artifact.id) but cannot change it: the host ignores any id a message carries.

E2 · The API

db.firestore  .get(path)                      → { id, path, exists, data }
              .set(path, data, { merge? })  .update(path, patch)  .delete(path)
              .add(collectionPath, data)    → { id, path }
              .list(collectionPath, { where?: [[field, op, value]…], orderBy?: [field, 'asc'|'desc'], limit?, startAfter? })
              .onDoc(path, cb) / .onList(collectionPath, query, cb)   → unsubscribe()
db.rtdb       .get(path)  .set(path, v)  .update(path, patch)  .push(path, v)  .remove(path)
              .on(path, cb)                  → unsubscribe()        (value events; the whole subtree)
db.storage    .upload(path, blob, { contentType? })  → { path, size }
              .url(path)                    → a short-lived URL the artifact can put in <img src>
              .list(prefix)  .delete(path)
db.kv         .get(key)  .set(key, v)  .delete(key)   per-viewer, per-artifact (artifacts/{id}/viewers/{uid}/kv)
db.serverTime                                 a sentinel; becomes the server timestamp in any write
db.me  ·  db.artifact  ·  db.ready  ·  db.on('readonly' | 'revoked' | 'build', cb)
  • Paths are the artifact's own view: '/my/doc' and 'my/doc' are the same, .. is refused, and a Firestore path must have an even number of segments for a document and odd for a collection, as Firestore requires. The prefix is added in the host: Firestore artifacts/{id}/db/data + path, RTDB /artifactData/{id} + path, Storage artifacts/{id}/files + path.
  • Values cross postMessage as structured clones. Firestore Timestamps arrive as Date, and a Date written becomes a Timestamp. References, GeoPoints and field transforms other than serverTime are not in v1.
  • Errors are plain: a rejected Promise with { code, message }, codes permission-denied, not-found, invalid-argument, quota, unavailable.

E3 · The broker, and why not a Firebase session in the iframe

  • The alternative was to give the artifact its own Firebase session: a custom token for a synthetic uid carrying an artifact claim, with rules keyed on it. It works, but it puts a live Firebase credential in the hands of the artifact's code, creates an Auth user per viewer per artifact, and forces every existing rule to learn to refuse that identity. The broker gives the same API with none of that: the only thing the artifact can ever cause is a call on its own prefix, made by our code.
  • Realtime still works: onDoc / onList / on are real listeners in the host, forwarding every snapshot into the iframe. The host caps them at 50 live listeners per artifact tab, and drops them all when the iframe goes away.
  • It cannot run outside TaskManager. An artifact is opened at /x/{id}, never on its own. That is the point: the host is where the sign-in and the sharing check happen.

E4 · The rules are the fence, not the broker

  • The broker is our code in the viewer's browser, and the viewer can change it (devtools). So the rules decide, exactly as for boards. Firestore: artifacts/{a}/db/data/{path=**} readable when access[uid] exists, writable when it is owner/editor, or viewer and not readOnly. The artifact document itself and its builds are read-only to clients; only commands write them.
  • RTDB cannot read Firestore, so the access map is mirrored to /artifactReaders/{id}/{uid}: role by a trigger, the same way boardReaders already works for presence.
  • Storage goes through the API for reads, as attachments do since phase 11 (the cross-service firestore.get() in Storage rules errors instead of denying). Uploads go straight to Storage under artifacts/{id}/files/ with a write rule that checks the role, and url(path) is a signed URL minted by /api/artifacts/{id}/files/url after the role check.
  • Limits the rules enforce: a Firestore document under 256 KB, an upload under 25 MB, and no writes when the artifact is archived.

E5 · Building one on your machine

  • Loaded outside a TaskManager host (vite dev, a file opened from disk), the driver says so in the console and switches to a mock backend: the same API over an in-memory store saved to localStorage, a fake me and a role you can set with ?role=viewer. An agent can build and click through an artifact without publishing it. db.mock is true so code can show a banner.

F · In the app

  • The sidebar gains ARTIFACTS under BOARDS (the sidebar is the map): each artifact you can open, starred ones first, and + New artifact. All artifacts lists the rest with who shared them and when they last changed.
  • The artifact page (/x/{id}) is the host of D3. Settings has four tabs: General (name, description, icon, read-only for viewers, archive), People (owner, editors, viewers, agents; add by email), Builds (the list with message, who, size, when; make current; drop a zip; download source), Data (a read-only browser of the Firestore and RTDB trees under the prefix, with the document count and bytes, and Delete all data for the owner).
  • Search (⌘K) finds artifacts by name. Notifications: being shared an artifact, and a new build on one you own, through the same per-person channel settings as everything else.

G · Data model

                                    agents { agentId: 'editor' }, readOnly, archived, currentBuild, createdAt, updatedAt

RTDB  /artifactReaders/{id}/{uid}   role, mirrored by a trigger

Storage artifacts/{id}/files/…      THE ARTIFACT'S STORAGE
  • Ids are Firestore auto ids; the URL is /x/{id}. No keys like board keys: an artifact is opened from the sidebar or a link, not typed.
  • Deleting goes through a queue like queueBoardDelete: the data subtree, the RTDB node, every Storage prefix, then the document.
  • Old builds beyond the newest ten (and never the current one) are removed by the daily housekeeping job.

H · What it costs

  • Artifact data is ordinary Firestore/RTDB traffic in the same project, so it counts against the same free quota (§W). A dashboard that lists 2,000 documents on every load is 2,000 reads per open. The Data tab shows each artifact's size, and the cost module of §X gets a per-artifact line from a counter the broker bumps (reads/writes per artifact per day, batched).
  • Serving files is a function call per file, so the first open of a build is roughly its file count in invocations; after that the browser cache answers (immutable, keyed by build). A typical Vite build is under 10 files.

I · Not in v1

  • Public or link-only sharing. Server-side code (functions) per artifact. Custom domains. Building from source on our side. Linking an artifact to a board or ticket (a Markdown link to /x/{id} works already; §K lets the page itself read and write a board's tickets). Firestore transactions and batched writes through the driver. Artifact-to-artifact data sharing.

J · What gets built

  1. Shared: schemas (Artifact, Build, access roles), the two scopes, the driver's message protocol as a typed union, path normalisation with its tests (the prefixing is the security boundary, so it gets the most tests).
  2. Backend: commands artifactCreate / Update / Share / Publish / SetCurrent / Delete / Open; zip unpack and checks; the capability sign/verify; /c/** file streaming; /api/artifacts/{id}/files/url; REST routes; MCP tools; the access-mirror trigger; the delete queue; housekeeping for old builds.
  3. Rules: Firestore, RTDB and Storage for the three prefixes, with emulator tests for every role against every path, and a test that a viewer cannot reach artifacts/{other}/….
  4. Hosting: the second site and its firebase.json target; /backend-driver/** on the app site; scripts/deploy.mjs deploys both sites.
  5. Driver: driver.js / driver.mjs / .d.ts and the mock backend; built and staged like the SDK.
  6. Frontend: sidebar section, /x/{id} host + broker, the four settings tabs, sharing, notifications.
  7. SDK, plugin, llms-full.txt: tm.artifacts.*, the artifact skill and Vite template, the generated chapter.
  8. End to end: publish a Vite React build and a plain HTML one from the SDK, open both as owner and as viewer, write from one tab and see it in the other, check that a removed viewer is refused, and check that artifact code cannot read the app's session (it throws on indexedDB.open).

K · A board's tickets, inside the page

A dashboard is most useful over the work itself. The owner can let an artifact use a board's tickets — read, or read and write — and the page builds whatever UI it wants with BackendDriver.tickets.

K1 · The grant is a ceiling, the viewer's role is the floor

artifacts/{id}.boards = { [boardId]: 'read' | 'write' }        // artifactBoardAccessSet, owner only
  • Who grants: the artifact's owner (Settings › Subscriptions, or artifactBoardAccessSet / MCP artifact_board_access_set). read needs them on the board; write needs them editor or admin there. null removes it — which either side may do: the artifact's owner, or an admin of that board (board settings › Subscribers lists the artifacts that use the board, through the app-only boardArtifactList; an artifact the admin is not on shows unnamed). At most 20 boards.
  • Who it works for: the broker in the host page acts as the viewer, exactly as for the artifact's own data (§E3). Reads are Firestore queries in the viewer's session, so the rules decide; writes are the ordinary ticket commands (ticketCreate, ticketUpdate, messagePost) as the viewer. So someone the artifact is shared with but who is not on the board sees nothing, and a board viewer cannot write through a write grant. The grant only ever takes away.
  • The fence: every tk.* op names a board by key (or a ticket key, whose prefix names it); one that is not granted is permission-denied, even for its admin. A write on a read grant is too. A read-only artifact (§B) stays read-only for its viewers, tickets included.

K2 · The API

db.tickets.boards()                         → granted boards I can read: { key, name, access, canWrite, stages, priorities, tags, fields, members }
db.tickets.list(board, query?)              → tickets   query: { stage?, assignee?: 'me' | email | id | null, state?, orderBy?, limit? }
db.tickets.onList(board, query, cb, onErr?) → unsubscribe (live)
db.tickets.get('ENG-42')                    → ticket | null
db.tickets.create(board, { title, description?, stage?, priority?, tags?, assignees?, dueAt?, startAt?, fields? }) → { id, key }
db.tickets.update('ENG-42', patch)          · db.tickets.comment('ENG-42', markdown)
db.tickets.thread('ENG-42', { limit?, before? })   → messages, oldest → newest (default the newest 50, at most 200)
db.tickets.onThread('ENG-42', [{ limit? },] cb, onErr?) → unsubscribe (live: the newest window, again on every change)
db.tickets.fileUrl('ENG-42', attachmentId)  → a short-lived URL (for <img>, <video>, <a href>)
db.tickets.aggregates(board, { field?, from?, to? }) → { field, from, to, total, count, lifetime, buckets: [{ key, total, count, tickets: { KEY: { total, count } } }] }
db.tickets.onAggregates(board, query, cb, onErr?)   → unsubscribe (live)

K3 · Reading threads and aggregates

Everything readable about a granted board is readable from the page — the same fence as tk.get: the board must be in the grant (read or write) and the viewer must be able to read it; anything else is permission-denied, and reads stay open to a read-only viewer.

  • Boards and tickets carry the aggregate fields: board.aggFields ([{ id, label, unit, period, archived }]), board.aggs and ticket.aggs ({ [fieldId]: { total, count } }; a board or ticket from before aggregates shows its legacy cost as aggs.cost).
  • A message is { id, kind: comment | system | question | agg, author, markdown, createdAt, editedAt, deleted, replyTo, pinned, attachments: [{ id, name, mime, size }], question?, agg?, run? }. A deleted message keeps its place as a tombstone (deleted: true, empty markdown and attachments). question is { title, status, blocking, fields: [{ id, label, type, required, options? }], answer: { values (by field label, choices by label), comment, by, at } | null }; agg is { at?, entries: [{ fieldId, label, unit, value }] }; run (a turn receipt) is { n, outcome, costUsd, durationMs, model }.
  • Paging. The broker reads the thread the way the app does (lib/ticket/data.ts): the inline window on the ticket document first, then the frozen data/{NNN} pages from the newest back, only as far as the request needs (each page fetched once per host page). before is a message id (page back with the first id you hold) or a time in millis. onThread follows the newest window and refuses before.
  • Files are never inline: fileUrl(key, attachmentId) goes through the app's file door as the viewer (/api/files/url, can(read) on the board) and only for a file of that ticket.
  • Aggregates read boards/{b}/aggStats/{period}:{key} by document-id range, as the app's Analytics does; one field (id or label, default the first active one), period keys inclusive, from defaulting to 30 days / 12 weeks / 12 months back like the REST GET …/aggregates. total and count sum the buckets returned; lifetime is the board's counter. Empty buckets are left out.

The mock backend (§E5) has all of it: the DEMO board's tickets carry threads (comments, a system line, an answered question, turn receipts, hours logged, an attachment, a tombstone) and the fields Cost ($, daily) and Time (h, weekly) with a month of buckets, so a page can be built outside TaskManager. The conversions are shared/artifacts/thread.ts and shared/artifacts/aggregates.ts.

Tickets come out with names, not ids (stage, priority, tags, people, select options), Markdown descriptions and millis times, and go in the same way; an unknown name is invalid-argument listing the ones that exist. The shapes and the conversion are shared/artifacts/tickets.ts; the driver's own documentation is §8.6 of llms-full.txt and the artifact skill.
