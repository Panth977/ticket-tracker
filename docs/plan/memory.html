Memory

A memory is a bucket of files you keep online: notes in Markdown, screenshots, videos, an APK, a spec, a logo. It is a concept of its own, next to boards and artifacts, with its own people. Inside it is a tree of folders and files that you browse as a tree or as folders, preview, and edit as code. What makes it more than a drive is reuse: a ticket can point at a memory file instead of carrying its own copy, an artifact's page can read (or write) one, and an agent can work in one over MCP. Files kept in a memory are managed — edited, moved, replaced, deleted — in one place, and every ticket that points at them sees the current version. Since §J a board takes no files of its own: every file put on a ticket goes into one of the board's memories.

A · What a memory is

  • A named bucket (memories/{memoryId}): name, description, an emoji, its people, and the boards and artifacts it has been granted to. Created at the root like a board or an artifact, listed in the sidebar under Memory, hideable from the sidebar, and bundleable into a workspace (agents.html §AB).
  • A tree of nodes (memories/{memoryId}/nodes/{nodeId}): a node is a folder or a file, with a parentId (null at the root), a name, and its full path (docs/brand/logo.svg) kept on the node so the tree, the breadcrumb and a lookup by path cost one listener and no joins. Paths are unique inside a memory; a move or rename of a folder rewrites the path of everything under it in the same batch.
  • The bytes live in Storage by file id: memories/{memoryId}/{fileId}/{fileName}. A node points at its current fileId. Saving a new version (an edit in code mode, a re-upload, an agent's write) writes a NEW file id and then deletes the old object, so a reader never sees a half-written file and a cached URL can never serve the wrong version.
  • Anything goes in: text, Markdown, code, images, video, audio, PDF, APK, zip. The mime type is taken from the upload (or the extension), and the app decides how to preview it.

B · People

Role May
owner everything, including share, grant to boards and artifacts, rename and delete the memory. Exactly one, the creator.
editor read, upload, edit, create folders, move, rename and delete files and folders.
viewer browse, preview, download.
  • Sharing is by email, like an artifact: memoryShare with a role, null removes; an address without an account becomes an invite.
  • Agents are not shared on a memory directly. An agent reaches a memory through a board it is on (§D). That keeps one place — the board — deciding what an agent may touch.
  • Being on a board gives nothing in a memory, unless the memory is granted to that board (§D).

C · Limits

name of a node 1–255 characters, no /, not . or ..
path ≤ 1024 characters, ≤ 32 levels
nodes per memory 10,000
one file, uploaded from the app 1 GB (straight to Storage)
one file, written through the API / MCP / driver 10 MB inline (text or base64)
memories per person (owned) 100
grants per memory 20 boards, 20 artifacts

D · Grants: a memory used by a board or an artifact

A grant is stored on the memory: memories/{m}.boards[boardId] and memories/{m}.artifacts[artifactId], each 'read' | 'write'. It is set with memoryGrantSet from the board's or the artifact's settings › Subscriptions (Add → pick the memory → tick Read / Write → Add; Edit; Remove), and the memory's settings › Subscribers list every board and artifact that uses it. Setting one needs BOTH sides: the caller owns the memory, and is an admin of the board (or the owner of the artifact). Ending one is either side's call (access: null): the memory's owner, an admin of that board, or the owner of that artifact — so a board admin can drop a memory they do not own from their board, and the memory's owner can drop a board they are not on. Like an artifact's board access (artifacts.html §K), a grant is a ceiling; what a particular person or agent can then do is bounded by their own role.

Grant Who May
board 'read' every member of the board, people and agents browse the memory, preview and download its files, attach them to tickets on that board
board 'write' editors and admins of the board (people and agents) also upload, edit, create folders, move and delete — through the API, MCP or the attach picker. Commenters and viewers still only read.
artifact 'read' / 'write' the artifact's page, acting as the viewer read (and write) through BackendDriver.memory, only as far as the VIEWER themselves can reach the memory — by a role on it, or through a board grant they are on.

memoryReach() (shared/src/memory/schema.ts) is the one function that answers "what may this principal do here", from the memory document, the principal's own role and their roles on the granted boards. Every handler, the file door and the driver broker call it.

E · Memory files on tickets

  • A reference, not a copy. messagePost, ticketCreate and ticketUpdate take memoryRefs: [{ memoryId, nodeId }]. Each becomes a row in ticket.files with source: 'memory', memory: { memoryId, nodeId } and the virtual path memories/{memoryId}/nodes/{nodeId}. Nothing is uploaded; the ticket's storage does not grow.
  • Attaching needs the grant: the memory must be granted to the ticket's board (read or write), and the caller must be able to comment there. The picker in the composer lists exactly the memories granted to the board.
  • Viewing resolves the live node. The file door (/api/files/url, agents.html §I) turns the virtual path into the node's CURRENT Storage object, so an edited file shows its new version on every ticket that points at it. Access: the viewer can read the board AND the memory is still granted to that board — or the viewer reaches the memory directly. A node that was deleted, or a grant that was removed, shows "No longer in memory".
  • Deleting a ticket never touches the memory; deleting a memory file leaves the reference row (it reads as gone).

F · The app

  • Sidebar › Memory: one row per memory (🧠 or its emoji), hideable like boards and artifacts; "All memory" lists them, archived included. /m is the list, /m/{memoryId} the memory, /m/{memoryId}?path=docs/a.md a file in it, /m/{memoryId}/settings/{general|people|access} its settings.
  • Two views, toggled in the header and remembered per browser: Tree (an explorer tree on the left, the open file on the right) and Folders (a breadcrumb and the current folder's contents as tiles with thumbnails; a click on a folder goes in, on a file opens it).
  • A file has two modes: Preview — Markdown rendered, images, video, audio, PDF, text with highlighting, and for anything else (an APK, a zip) its facts and a Download button — and Code — the file as text in a code editor, editable by editors, saved with ⌘S or Save (memoryFileWrite; a new version). A binary file in Code mode shows its facts and Replace… instead of bytes.
  • Uploads: drop files or whole folders onto the tree or a folder, or Upload. The browser uploads straight to Storage (progress per file), then memoryFilePut registers each node. Files picked with Upload first ask where they go: one field per file holding its full path, folder and name together (/docs/brand/logo.svg, the open folder filled in); a picked folder gets one field for the folder it becomes. A path where a file is replaces it; one where a folder is is refused.
  • Menus: Rename (F2), Move to…, Copy path, Download and Delete (Del) are on every node's menu, and New file / New folder / Upload in its folder. The same menu opens on a right-click — on a node, or on the empty space for the folder itself. A name field takes a path: / separates folders, created as needed, and a leading / starts from the top — so old/a.md as a rename of docs/a.md moves it to docs/old/a.md. The open file's name is a rename button too.
  • Dragging a node (or files from the desktop) lights up the folder a drop would land in, wherever it shows: its whole subtree in the tree, its tile, its breadcrumb, the folder view. Over a file, that is the file's folder; a folded folder unfolds after a moment; a pill by the pointer says Move … into /path. A folder never lights up for itself or what is inside it, nor for the folder the node is already in.
  • Board settings › Memory and Artifact settings › Memory: the memories I own, each with none / read / write.
  • Workspaces: a workspace bundles memories too (memoryIds); entering one through it keeps the workspace crumb and switcher.

G · API

Scopes memory:read and memory:write (consent group "Memory"). An account token or an OAuth grant reaches the memories its person reaches; an agent token reaches only those granted to a board the agent is on. Every node is named by path (or nodeId); writing a path creates its missing parent folders.

Command What
memoryCreate / memoryUpdate / memoryDelete the bucket (delete is queued: Storage, nodes, then the document)
memoryShare a person's role, by email
memoryGrantSet a board's or an artifact's access (§D)
memoryList the memories I reach (optionally: those granted to one board or artifact)
memoryTree every node under a folder (default: all), for a reader who is not on the memory itself
memoryFileRead a file's text (≤ 1 MB, else truncated) or a signed URL
memoryFileWrite create or replace a file inline: text or base64, ≤ 10 MB
memoryFilePut register a file the app uploaded to Storage itself
memoryFolderCreate, memoryMove, memoryNodeDelete folders, rename / move, delete (recursive)

MCP: every command above is a tool (the bridge, agents.html §AB's neighbour), plus show_memory in chat. REST: GET /v1/memories, GET /v1/memories/{id}/tree, and the raw bytes at GET|PUT /v1/memories/{id}/files/{path} for files over the inline limit.

I · Decisions

  • D-M1 · Tree in Firestore, bytes in Storage. One listener draws the whole tree (10k nodes at most, each a few hundred bytes); Storage listing would need a call per folder and cannot hold empty folders or a rename.
  • D-M2 · A new version is a new object. Overwriting in place would let a cached URL serve a mix, and a failed write would corrupt the only copy. The old object is deleted after the node points at the new one.
  • D-M3 · Tickets point at the node, not the version. That is the point of keeping it in memory: fix the screenshot once. A ticket that must freeze a version should upload a copy, as before.
  • D-M4 · Agents through boards only. A third place to put an agent would be a third place to forget to remove it.
  • D-M5 · A board takes no files of its own (§J). Two homes for a ticket's file — the board's prefix and a memory — meant two sets of rules, two sweepers and two answers to "where is that screenshot". One home: the memory, where it can be found, moved, reused and cleaned up.

J · Ticket attachments live in a memory

A file put on a ticket — from the composer, a new ticket's description, the API, the intake widget or an e-mail — is uploaded into a memory granted write to the board and becomes a NEW file there. The ticket holds a reference exactly like §E: a row with path = memories/{m}/nodes/{n} and memory: { memoryId, nodeId }. Rows and objects from before (Storage boards/{b}/tickets/{t}/{a}/{name}) keep working for reading, downloading and deleting; nothing new is written there.

The board's default: board.attachMemory

  • boardAttachMemorySet { boardId, attachMemory: { memoryId, template } | null } — board admin, never an agent; the memory must exist, not be deleting, and be granted write to the board. Written only by the server (boards are not client-writable).
  • The template is a path with variables: <ticketId> (the key, ENG-42), <time> (UTC, 20261005-211946), <random6>, <filename>, <exe> (the extension; <ext> is the same). Default: tickets/<ticketId>/<time>_<filename> (shared/src/memory/attach.ts).
  • Kept true: memoryGrantSet clears it (same transaction) when that board's grant is removed or lowered to read; memoryDelete clears it on every granted board.

From the app: memoryUploads

  • The app uploads to memories/{m}/{fileId}/{name} with metadata { boardId }. storage.rules lets the board's admin, editor or commenter create it when the memory is granted write to that board and is neither archived nor deleting (≤ 1 GB) — besides the memory's own owner / editors as before.
  • messagePost / ticketCreate take memoryUploads: [{ memoryId, path, storagePath }] (≤ 20). A <ticketId> left in the path is filled with the ticket's key. attachments (board storage paths) is retired: a non-empty list is a 400.
  • Permission is the board's, not the person's memory role: the memory is granted write to the board, not archived, not deleting; the command has already checked the caller may post there. So a commenter with no role on the memory can add a file to it — but only a NEW one: an existing node is never replaced. A taken path (file or folder) becomes name (2).ext, (3)…; a parent that is a file is a 400. Parents are created as usual.
  • One commit. The new nodes are planned and written inside the command's own transaction (backend/src/memory/attach.ts planMemoryUploads), together with the message or the ticket. ticketCreate knows the key there: it is board.key-nextNumber, read before any write, the very number allocateKey then issues. So a refused or failed post leaves no file in the memory and no row pointing at nothing. When the command fails after the uploads were checked, the uploaded objects that no node points at are deleted (like a failed memoryFilePut); a retried request whose objects are already nodes reuses them.

Bytes the server holds

  • POST /v1/tickets/{KEY}/files and MCP upload_file write the bytes into the board's attachment memory (or the request's memory_id, at path when given) and, in one transaction, the new node and the ticket's upload row (source: 'upload', messageId: null, path = the reference). fileIds on post_message works unchanged. No attachment memory and no memory_id: 400 "This board has no attachment memory — set one in board settings › Memory".
  • The intake widget and inbound e-mail store their files the same way, with <ticketId> left for ticketCreate / messagePost to fill. A board with no attachment memory still gets the report or the reply — without its files, and with a line saying so ("2 attachments were not saved: this board has no attachment memory — board settings › Memory").
  • Housekeeping sweeps abandoned objects under boards/ only. A memory file is the memory's, whether or not its ticket row is ever posted in a message; deleting a message or a ticket never deletes it.

Known gaps: an intake or e-mail retried after it already succeeded (idempotent replay) leaves its fresh copies as objects no node points at; nothing sweeps memories/ for those yet. A board-scoped token acting as a person reaches no memory (§G), so it cannot read back a ticket file that lives in one.
