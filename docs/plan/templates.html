Templates

A board's own UI, written as code. Panth asked (ORCH-8, 2026-10-16) for message templates "where based on field1 dropdown selection the next form fields are set" — something a fixed form builder cannot express and a few lines of JavaScript can. A template is that JavaScript: a board's admins write it (or ask an agent to), and it shapes three places — a form in the composer, a form in New ticket, and the cards of a kanban view. The reference a template author reads is §9 of /integrate (also get_template_docs over MCP and the plugin's template skill); this page is why it is built the way it is.

A · The thing

  • boards/{b}/templates/{id} — { kind, name, description, indicator?, code, position, createdBy, createdAt, updatedBy, updatedAt } (@tm/shared TemplateSchema). kind is message | ticket | card and never changes (a view names a card template; a form could not stand in). ≤ 50 per board, ≤ 100 000 characters of code each.
  • Indicator + description like every entity (indicators.html): the composer's menu, New ticket's row and the settings list draw them.
  • Admins write, the board reads. templateSave / templateDelete are can(admin) (scopes board:admin, boards:admin — an agent that is a board admin may too); the security rules let every reader of the board read the collection. Decided by Panth: admins only — the code runs in everyone's browser.
  • Deleting a card template sets cardTemplateId: null on every view that used it, in the same transaction. Copying a board (boardCreate { fromBoardId }) copies its templates under new ids and re-points the copied views.

B · Where the code runs

The one decision that shapes everything. A card template runs in the browser of everyone who opens the view; in the app's page it would hold their Firebase session — an admin's template could act as any member who looks. So it never runs in the page. Panth's choice (of three: worker + virtual DOM, a sandboxed iframe per form, trusting authors): "All this code will be run in frontend and ideally on a separate thread and communicate via API, while the render engine remains in the main thread."

  • B1 · A worker with an opaque origin. host.ts starts worker/runtime.js as a module Worker from a data: URL. A worker from a blob: URL would share the app's origin — and with it the IndexedDB where Firebase keeps the refresh token. A data: worker's origin is null: indexedDB.open throws, there is no localStorage, a relative fetch has no base, an absolute one to the app is cross-origin without credentials. Probed in Chromium and WebKit before building, and asserted by e2e templates.spec (idb:blocked local:none api:unreachable origin:null).
  • B2 · api is the only door. The worker asks; the page answers with the viewer's own reads of this board only (bridge.ts: board, members, tickets get / list / search from the live list the board screen already keeps, a small per-person store). Never another board — a template could fetch() what it reads to anywhere, so it may read only what its author, an admin of that board, can already see. Never a write: the only thing a template sends is its submit answer, when the person presses the button.
  • B3 · The render engine stays in the page. render returns a tree of the builder's node types (protocol.ts); functions become handler ids. render.ts draws it with the app's own classes and patches on every new tree: a node keeps its DOM element while its type and slot (or key) match, a hole (cond && h.x() that is false) keeps its slot, and a node already in place is never moved — so the input being typed in keeps focus and caret while fields appear and vanish around it.
  • B4 · Typing never goes backwards. Every event carries a sequence number; every tree carries the newest one the worker had seen (ack). A controlled input is written only when ack has caught up with the last event it sent, so a render computed before your last key cannot undo it. (The e2e test types 56 characters at 5 ms each and compares.)
  • B5 · No HTML from a template. Text is text; h.markdown goes through the app's sanitising renderer; h.el takes a fixed list of tags; style refuses url(), expression() and script; links are http(s), mailto or app paths; images https or inline raster.
  • B6 · A watchdog. The page pings every second; three seconds without a pong (an endless loop) and the worker is terminated, with "The template stopped responding" in the form. Errors carry the template's line (the runtime measures where line 1 sits inside new Function).

C · The module

export default { state?(ctx), render(state, setState, h, ctx), submit?(state, ctx) } — Panth's sketch (render(state, setState, builder), onsubmit(state) → { type: 'valid' | 'invalid' … }) kept almost word for word. setState merges and batches one render per microtask. ctx is plain, named data: the board with its stages, priorities, tags and fields; the viewer; for message templates the ticket of the thread, for cards the card's ticket (info.ts — fields by name with readable values, and by id as stored).

D · What a submit does

  • D1 · Message. { type: 'valid', msg, data? }: msg is Markdown, turned into the rich doc in the page (mentions as @email, #KEY refs of the board) and sent through the same outbox as a typed reply with markdown beside it. data (JSON ≤ 16 000 characters) is stored as Message.template = { id, name, data } — the server checks the template exists and writes its current name — and every door returns it, so an agent reads the form's answer instead of parsing prose.
  • D2 · Ticket. { type: 'valid', ticket } names things as people do — a stage or tag by name, a person by email, a field by name — and resolve.ts turns names into ids. A tag name the board lacks becomes a tag (as quick add does); anything else that names nothing is listed and nothing is created. Required fields must be set. The create is the full form's: queued, a pending card at once.
  • Invalid keeps the form open: errMsg above the buttons, and error: { name: message } under the input with that name.

E · Card templates

  • A kanban view's cardTemplateId (ViewSchema; viewSave checks it names a card template of the board). Chosen in the view bar's Layout menu, or when creating a view with + (Panth: "click on + in view tabs, create a custom board view and there you will get the option to set the preview").
  • One worker per template, shared by every card (cards.ts): the asks of one tick go as one batch, and a card's tree is kept until its ticket's updatedAt changes. Drawn static — no handlers; the card opens the ticket.
  • While a card's tree is on its way, or when the template throws for that ticket, the built-in card stands in, with a ⚠ naming the error. Calendar chips and the table stay built-in.

F · The editor

Settings › Templates lists the three kinds (and keeps "Copy this board" below). ?t={id} opens one: name, indicator, description; the code in CodeMirror (⌘S saves); a live preview that restarts 600 ms after typing stops, against a ticket of the board you pick; the template's console; errors with a line that jumps the cursor; and Try submit, which shows what would be posted or created without sending it. Non-admins can read the code and try it.

G · For agents

"Add all these features to MCP too, so we can ask AI to build this for us": the commands are bridged as template_save / template_delete like every command with scopes; list_templates (with include_code) and get_template_docs (the reference text + a starter per kind) are reads; view_save takes cardTemplateId. The reference text lives once, in @tm/shared TEMPLATE_DOCS_MD, and is printed by the MCP tool, §9 of llms-full and the plugin's template skill. SDK 2.1.0 (the public message shape gained template).

H · Not in v1

  • Templates for the table, calendar or timeline; per-person templates.
  • Writes from a template through api (moving, assigning) — by design.
  • Reading other boards, archived tickets, or a ticket's thread from api.
  • Versions / history of a template's code (the editor saves over).
